# Smnpm: rule-derived tests for menvcfg.PMM, and the pointer-masking rules about several modes

One of five pointer-masking suites (Smmpm, Smnpm, Ssnpm, Sspm, Supm) generated by `gen/gen_Spm.py`. A rule goes to
the suite whose behavior it constrains. This suite holds the menvcfg.PMM rules and the zpm.adoc rules that relate
several modes' settings (per-mode control, MPRV, UXL/SXL, illegal WARL writes). Every file boots to M-mode, owner of
menvcfg, and requires Sm; S- and U-mode accesses run in windows entered with mret, and traps return to M-mode (the
M boot delegates nothing).

## How the extension is tested

- `menvcfg_pmm_op` (requires S) and `menvcfg_pmm_op_noS` (forbids S, MU harts), `smnpm_definition`: menvcfg.PMM
  masks S-mode, or U-mode when S is absent, and not M-mode or (with S) U-mode.
- `menvcfg_pmm_enc`: the WARL encodings, the csrrw/csrrs/csrrc forms, and the other menvcfg fields untouched.
- `pm_config_next_higher`, `pm_per_mode_control`, `pm_auto_apply_active_mode`: mseccfg (Smmpm), menvcfg and
  senvcfg (Ssnpm) set alone, together with different values, and with accesses alternating between modes without
  reconfiguration. Every mode present is checked against its own register's read-back value.
- `pm_mprv_spvp`: MPRV=1 with MPP = M, S and U uses the MPP mode's setting, with Bare and Sv39 (sign extension of
  S- and U-level VAs through supervisor and user tables). The SPVP half (HLV/HSV) is in the H suite
  (`hstatus_hupmm_*`).
- `pm_mxr_exception`: MPRV with MXR=1: S/U effective modes are not masked, M is. Expectations for MPP=M come from
  mseccfg only when Smmpm is implemented (mseccfg may not exist otherwise).
- `pm_uxl_clear`: SXL=1 (UXL=1 without S) clears menvcfg.PMM, writes are then ignored, and PMM stays 00 when XL
  goes back; where XL is read-only the ignored write must leave PMM alone.
- `pmlen_illegal_warl`: 01, 10 and 11 written from 00 and from 11 to each register; whatever legal value results,
  the hart masks according to it.
- `pm_deterministic_effect`: one transformation predicts M, S and U physical accesses and S/U Sv39 accesses.
- `menvcfg_pmm_rdonly0` (FORBIDDEN Smnpm) and `pm_rv32_illegal` (requires only Sm): read-only zero without Smnpm and
  on RV32 (menvcfgh, mseccfgh, henvcfgh bits 1:0). RV32 harts cannot have pointer masking, so these files do not
  require the extension; each CSR is probed with a read in a trap window first.

## Rules not tested here

- `pm_rv64_only` is the definition that `pm_rv32_illegal` and the `*_rdonly0` tests make observable.
- `pmlen_mode_depend` is a permission (the supported PMLEN values may differ per mode); every test reads each mode's
  value back instead of assuming one.
- `pm_debug_trigger` (masking of Sdtrig address matches) is not generated yet: it needs trigger setup, which belongs
  with the Sdtrig suites.
- `pm_no_trap_vector_mask` is not tested: it needs a tagged stvec/mtvec, but those are the framework's trap vectors
  (and a tagged address is invalid, so the WARL register may hold another value).
- The other zpm.adoc rules are in Smmpm (M-mode), Sspm (S-mode), Supm (U-mode) and Ssnpm (VS/VU, guest-physical).

## Subtleties

- Scope: the `*_rdonly0`, `*_absent` and `pm_rv32_illegal` files test the "not implemented" and RV32 halves of the
  rules. They require only the modes they use and forbid the extension (an RV32 hart can never have it), so they run
  on harts without the extension; they sit in the extension's directory because that is the rule's home.
- The multi-mode rules here boot to M and require Sm, so profiles without Sm (RVA23) do not get them; their S, U
  and VS/VU behavior is covered per mode in Sspm, Supm and Ssnpm.
- A failing SC to an address that fails its access check (no reservation) is accepted either to trap or to fail
  without writing: zalrsc.adoc says "No sc.w instruction shall retire unless it passes memory permission checks",
  but whether an access fault from a missing PMA region is a "permission check" is not clear, and the rule is SC's,
  not pointer masking's. QEMU fails such an SC without trapping.

- MXR is never in effect for an access whose effective mode is M
  ([#3313](https://github.com/riscv/riscv-isa-manual/issues/3313),
  [#1915](https://github.com/riscv/riscv-isa-manual/issues/1915)); for S/U effective modes it disables masking even
  with Bare translation, for every explicit access.
- The ignore transformation comes before the validity check
  ([#1944](https://github.com/riscv/riscv-isa-manual/issues/1944)).
- Fetch addresses are never masked, also not when written to xtval
  ([#2423](https://github.com/riscv/riscv-isa-manual/issues/2423)).
- All the configurations here have XLEN fixed at 64, so `pm_uxl_clear` runs only its read-only path.

## Shared mechanics (all five pointer-masking suites)

The five suites come from one generator, `gen/gen_Spm.py`, with helpers in `gen/spmlib.py` (and page tables from
`gen/hmem.py`). Pointer masking exists only on RV64, so behavioral files have their body under
`#if __riscv_xlen == 64`; the read-only-zero files also run on RV32.

- **PMM is WARL, probed at run time.** After every PMM write the test reads back what the hart holds, checks it is a
  legal value (00, 10 or 11; 01 is reserved), and branches on it: each legal value has its own expectations
  (`dispatch` in `spmlib.py`). A hart that supports only PMLEN=7, only 16, or neither for some mode is tested on
  what it holds. The encoding tests require at least one of 10 and 11 to be supported, because the extension
  "provides pointer masking".
- **Expected outcomes come from the ignore transformation** (`spmlib.transform`): virtual addresses are
  sign-extended from bit XLEN-PMLEN-1, physical and guest-physical ones zero-extended. Each access is built at run
  time from an untagged base with its top 7 or 16 bits replaced by a tag. Masked: the access reaches the untagged
  location (loads return its data; stores, AMOs, SC and CBO.ZERO change it, checked through an untagged load).
  Not masked: an access fault (physical: bits 63:56 are never a valid physical address; a high tag bit in 55:48
  is assumed to hit no memory), a guest-page fault (beyond the 41-bit Sv39x4 GPA range), or a page fault
  (non-canonical VA), and nothing is written.
- **Tags.** All of bits 63:57, 0x55/0x2A patterns, 0xA5C3 in 63:48 (only PMLEN=16 masks it), and single bits 63,
  57 (lowest bit PMLEN=7 masks), 56 (XLEN-PMLEN-1 for PMLEN=7: never masked by it; sign bit for VAs), 48 (lowest
  bit PMLEN=16 masks) and 47.
- **Virtual addresses.** satp (or vsatp) Sv39, Sv48 and Sv57 are each probed: an unsupported MODE leaves satp
  unchanged. Tables identity-map the root-level page holding the test image and map the last root-level page (top
  of the high half) to the same page, so page A is reachable at a positive and at a negative VA. A high-half
  address whose top bits are cleared reaches A only by sign extension. With Sv57 and PMLEN=16, bits 56:48 select
  the root entry, so a design that only relaxes the validity check (instead of sign-extending) reads the wrong
  entry.
- **xtval.** A fault on a transformed address that is a valid VA must report 0 or exactly that VA (an unmapped
  root entry). A fault on an invalid address may report 0, the address, or another invalid address (stval/mtval
  rules), so the test only requires that it is not the masked, valid address. A misaligned page-crossing access
  may also report the start of the second page.
- **Every write of 00 must read 00** (00 is always legal), and suites that promise masking (Sspm, Supm, the
  `*_pmm_enc` tests, henvcfg) require that writes of 10 and 11 do not both read 00.
- **Misaligned accesses**: when the tag is masked, the untagged access runs first and the tagged one must trap
  exactly when it did ("the same limitations as in the absence of pointer masking").
- **Software CSR writes** (`pm_no_csr_sw`, `pm_warl_unaffected`) use only valid addresses (negative Sv39/48/57 VAs
  when the scheme is supported, the image address), which must read back exactly; tagged values are invalid
  addresses that a WARL xepc/xtval need not hold.
- **Traps** are checked in the framework trap log: count, cause, xepc (except fetch faults), the computed xtval
  predicate, and the mode the trap came from. Instructions outside RV64I (AMOs, LR/SC, FP, vector, CBO.ZERO) are
  `.word` encodings run only under `#if <EXT>_SUPPORTED`, so MARCH stays `rv64i_zicsr_zifencei`.
- **Mutation check.** `gen_Spm.py` has a `MUTANTS` dict (`Spm:<mutant>` in `gen/mutate.py`): wrong sign/zero
  extension, off-by-one PMLEN, swapped encodings, Sv57 validity-only masking, masked fetch or page-table walk, MXR
  ignored / applied to M / loads only, the wrong register controlling a mode (menvcfg for U, senvcfg for S or VS,
  mseccfg for S/U, menvcfg for M, henvcfg for VU, M's setting under MPRV), 01 reading back, untransformed xtval,
  masked software CSR writes, per-class unmasked accesses (AMO, LR/SC, FP, vector, CBO.ZERO, sub-word),
  unmasked second half of a page-crossing access, an ignored UXL write clearing PMM, writable RV32 PMM bits, a
  PMM change needing SFENCE.VMA, and no nonzero PMLEN. Every mutant fails at least one test on Sail (rv64; the
  RV32-only `rv32_pmm_writable` on sail-rv32-max).
