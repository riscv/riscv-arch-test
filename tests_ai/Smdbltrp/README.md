# Smdbltrp: rule-derived tests for the M-mode double-trap extension

The Smdbltrp chapter (`src/priv/smdbltrp.adoc`) only names the extension. The rules are tagged in `machine.adoc`
("Double Trap Control in mstatus Register" and the MRET/SRET/MNRET paragraph after it). Generated by
`tests_ai/gen/gen_Smdbltrp.py` (with `gen/dbltrplib.py`), which also writes [`../Ssdbltrp`](../Ssdbltrp/README.md).

## How the extension is tested

- **Boot.** Every test boots to M-mode (medeleg = mideleg = 0), so every trap from S, U, VS and VU goes straight to
  M-mode. The framework's M handler records mstatus (mstatush on RV32) on entry, before it changes anything, so the
  trap log shows MDT as the trap left it.
- **No unexpected trap is taken on purpose.** A trap into M-mode with MDT=1 ends the run (critical-error state) or,
  with Smrnmi, enters the RNMI handler at an implementation-defined address. Tests take no trap while MDT=1. Rules
  whose result is only visible in a lower mode (MRET/SRET/MNRET into S, U, VS, VU clear MDT) are checked by taking an
  ordinary ebreak there: it must be logged as a normal trap. A hart that left MDT=1 ends the run instead.
- **MDT as a field** (`mstatus_mdt_sz_warl`): csrs/csrc/csrw/csrrs/csrrc/csrrw on mstatus (RV64, bit 42) and mstatush
  (RV32, bit 10), read-only forms, and writes of other bits.
- **MDT and MIE** (`mstatus_mie_*`): mie is 0 while MIE is set, so no interrupt is taken. Setting MDT by every
  register form clears MIE (on RV32 a write of mstatush clears a bit of mstatus); writes that leave MDT=0 do not;
  with MDT=1 every form that writes MIE=1 (including csrsi) leaves it 0; on RV64 a single write of MDT=1 and MIE=1
  leaves MIE=0, and a single write of MDT=0 and MIE=1 sets MIE.
- **Trap entry** (`trap_exp`): ebreak, an illegal instruction (csrrw to mhartid) and a load access fault from M-mode,
  ebreak from S and U, and a supervisor software interrupt taken in M-mode: MDT=1 at handler entry, MDT=0 after
  the handler's MRET.
- **MNRET** (`mstatus_mdt_clr_mnret`, requires Smrnmi): executed in M-mode without an RNMI, with mnepc and
  mnstatus.MNPP/MNPV preset. MNPP=M leaves MDT unchanged.
- **Mutation check.** `MUTANTS` in `gen_Smdbltrp.py` (shared with Ssdbltrp) are expectation switches. The Smdbltrp
  mutants fail a test on Sail RV64, except `mnret_m_clears_mdt`, which needs Smrnmi (Whisper only).

## Rules not tested here, or only partly

- **Not observable:** `mstatus_mdt_rst` (the framework writes MDT=0 before the test starts);
  `trap_unexp_mdt_1`, `trap_unexp_mnstatus_nmie_0`, `trap_unexp_hndl_lead_in`, `trap_unexp_hndl_no_rnmi` (the hart
  ceases execution, so no test can pass after the unexpected trap; whether the platform sees the critical-error signal
  is outside the architecture).
- **Blocked by the framework:** `trap_unexp_hndl_rnmi` and `Smdbltrp_with_Smrnmi_op` need the RNMI trap handler
  address, which is implementation-defined and has no RVMODEL macro (Whisper's default `nmi_vec` is 0, where its
  PMA has no memory). `trap_unexp_rnmi` and `mstatus_mdt_not_set_rnmi` also need a way to raise an RNMI.
- **Other suites:** `medeleg_16_rdonly0` (Sm).
- **Partial:** `mstatus_mdt_clr_mret_sret` and `mstatus_mdt_clr_mnret` see the cleared MDT directly only for a
  return to M-mode; for S, U, VS and VU they rely on the next trap being delivered normally.

## Subtleties

- A write of MDT 1 -> 1 also counts as setting MDT, and the state MDT=1, MIE=1 cannot be reached
  ([#3155](https://github.com/riscv/riscv-isa-manual/issues/3155)).
- With Smdbltrp and Smrnmi, an exception in M-mode with mnstatus.NMIE=0 is a critical error whatever MDT is
  ([#3254](https://github.com/riscv/riscv-isa-manual/issues/3254)). The framework boots with NMIE=1.
- The MRET/SRET paragraph applies to MRET, and to SRET executed in M-mode; its U/VS/VU clause is qualified by
  execution in M-mode ([#2870](https://github.com/riscv/riscv-isa-manual/issues/2870)).
- QEMU RV32: any write of mstatus clears mstatush.MDT, and with MDT=1 csrsi sets MIE (`mstatus_mdt_sz_warl`,
  `mstatus_mie_set_mdt_0` fail); the same mechanism as
  [qemu#4488](https://gitlab.com/qemu-project/qemu/-/issues/4488) for MPELP, which mentions MDT as unchecked.
  QEMU's mstatus.MPV is read-only zero ([qemu#4588](https://gitlab.com/qemu-project/qemu/-/work_items/4588)), so the
  VS/VU parts of `mstatus_mdt_clr_mret_sret` fail there.
