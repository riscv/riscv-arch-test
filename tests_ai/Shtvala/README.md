# Shtvala: rule-derived tests for htval holding the faulting guest physical address

One test for the only `norm:` rule in `src/priv/shtvala.adoc`. Generated by `tests_ai/gen/gen_Sx.py`. Mutants are
named `Sx:htval_*`.

## How the extension is tested

- **Strict htval.** Without Shtvala, htval may be 0 on a guest-page fault. Here it must be GPA >> 2, with the
  offset bits above bit 1 kept. stval is not constrained here: Sstvala is another extension.
- **G-stage.** Sv39x4 (RV64) or Sv32x4 (RV32), probed.
- **Faults:**
  - HLV.W, HLVX.WU and HSV.W of an unmapped GPA;
  - VS-mode lw, sw and a fetch, and a VU-mode lw;
  - misaligned HLV.W and VS lw into an unmapped page, where htval is the page boundary's GPA;
  - a VS-stage leaf that maps a guest virtual page to an unmapped GPA, so htval must be the GPA, not the guest
    virtual address;
  - implicit VS-stage page-table reads. The VS tables live at GPAs, and each level's table in turn is unmapped at
    G-stage, so htval is the GPA of the PTE that was read.

## Rules not tested here

- Guest-page faults taken in M-mode write mtval2, which Shtvala does not cover.

## Subtleties

- **Implicit accesses.** For a guest-page fault on an implicit VS-stage access, the faulting GPA is the PTE's
  address (`H_trap_xtinst_guestpage`), not the final data address.
- **Exact GPA.** htval is the exact faulting GPA shifted right by 2, so its offset within the page matters.
- **stval = 0.** For an explicit access, a nonzero htval must correspond to the address in stval
  (`mtval2_htval_virtaddr`). So when the hart writes stval = 0, htval = 0 is accepted too; with a nonzero stval,
  only GPA >> 2 is.
- **Known DUT bug.** QEMU raises an instruction page fault for HLVX of an unmapped GPA
  ([qemu#4595](https://gitlab.com/qemu-project/qemu/-/issues/4595)), so this test fails on qemu-rv64-max and
  qemu-rv32-max.
