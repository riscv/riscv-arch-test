# Ssdbltrp: rule-derived tests for the S-mode double-trap extension

The Ssdbltrp chapter (`src/priv/ssdbltrp.adoc`) names the fields (`menvcfg.DTE`, `sstatus.SDT`, `henvcfg.DTE`,
`vsstatus.SDT`). The behavior is tagged in `supervisor.adoc` ("Double Trap Control in sstatus Register"),
`machine.adoc` (menvcfg.DTE; MRET/SRET/MNRET clearing SDT) and `hypervisor.adoc` (vsstatus.SDT). Generated by
`tests_ai/gen/gen_Smdbltrp.py` (with `gen/dbltrplib.py`), which also writes [`../Smdbltrp`](../Smdbltrp/README.md).

## How the extension is tested

- **Boot.** S-level rules boot to S-mode and set `menvcfg.DTE` through T-SBI. The MRET/MNRET rules and the mstatus
  view of the SIE rule are `_Sm` files that boot to M-mode (medeleg = 0) and require Sm (and Smdbltrp, which the
  MRET paragraph is part of).
- **Fields.** DTE and SDT read back 0 and 1 through every register CSR form; SDT is one bit seen as sstatus.SDT and
  mstatus.SDT; henvcfg.DTE and vsstatus.SDT are writable once menvcfg.DTE (and henvcfg.DTE) is 1, and VS-mode
  reaches vsstatus.SDT through sstatus.
- **SDT and SIE.** sie (mie in the `_Sm` file) is 0 while SIE is set. Every register form that sets SDT clears SIE,
  also when the same write sets SIE; with SDT=1 every form that writes SIE=1 leaves it 0; a single write of SDT=0 and
  SIE=1 sets SIE; writes that leave SDT=0 do not touch SIE.
- **DTE=0** behaves as though Ssdbltrp were not implemented: SDT reads 0 after DTE is cleared while it was 1, an
  S-mode ebreak is then delivered to S-mode (not as a double trap), SDT writes neither stick nor clear SIE, traps
  into S-mode leave SDT=0, and henvcfg.DTE and vsstatus.SDT are read-only zero. After DTE is set again, SDT reads 0
  or 1.
- **Trap entry.** ebreak, load and store access faults (`RVMODEL_ACCESS_FAULT_ADDRESS`) and a misaligned load from
  S-mode, ebreak from U, VS and VU (into HS-mode, hedeleg = 0), and a supervisor software interrupt in S and U: SDT=1
  at S handler entry, SDT=0 after its SRET.
- **Double trap.** With SDT=1 in S-mode, the same exceptions (the misaligned load may also complete) are taken by the
  M handler with mcause 16; scause, sepc, stval and sstatus.SPP/SPIE keep their presets and SDT is still 1 when the
  M handler returns; mepc is the instruction, mtval is the unexpected trap's (0 or pc, or 0 or the address), MPP=S,
  MIE=0, and with H MPV=0, GVA=0, mtinst=0 for ebreak and mtval2 = the unexpected trap's cause.
- **VS level** (`vsstatus_sdt_op`, requires H): with both DTE bits set and hedeleg delegating breakpoints and load
  access faults, a trap into VS-mode sets vsstatus.SDT; with vsstatus.SDT=1 it becomes a double trap into M-mode
  (origin VS, mtval2 = cause, vsepc/vscause/vstval untouched); with henvcfg.DTE=0 it is delivered to VS-mode.
- **SRET** in S-mode clears SDT: read directly for SPP=S; for U, VS and VU, the next trap into HS-mode must be an
  ordinary one.
- **MRET, SRET in M-mode (to U, and with hstatus.SPV=1 to VS and VU), MNRET** (`_Sm`): after the return, an ebreak traps straight back to M-mode, whose handler
  records sstatus.SDT; vsstatus.SDT is read in M-mode.
- **Mutation check.** `MUTANTS` in `gen_Smdbltrp.py`. Each Ssdbltrp mutant fails a test on Sail RV64, except the
  MNRET ones (Smrnmi is only on Whisper; see Subtleties).

## Rules not tested here, or only partly

- **Other suites:** `menvcfg_dte_sdt_rdonly0` (S, the hart without Ssdbltrp), `henvcfg_dte_op`, `sret_dt` and
  `mtval2_Ssdbltrp` (H).
- **Partial:**
  - Double-trap classes: illegal instructions are not used (the framework routes them through M-mode for emulation, so
    they never reach S-mode as a hardware trap), nor fetch faults (with C, the M handler reads the instruction at mepc to
    step past it, which faults again inside the handler with MDT=1). Interrupts cannot be unexpected traps into
    S-mode: SIE is 0 whenever SDT is 1 in S-mode, and U, VS and VU are only entered with SDT=0.
  - `sstatus_sdt_double_trap_mtval2` requires H: the framework records mtval2 in the trap log only with H.
  - SRET in M-mode to S-mode is executed but its SDT result is not checked (see Subtleties), nor is SDT after DTE is
    set again (`menvcfg_dte_op`).
  - `sstatus_sdt_sret` and the MRET/MNRET rules see a cleared SDT in U/VS/VU only through the next trap.

## Subtleties

- SRET executed in M-mode with SPP=S: [#2403](https://github.com/riscv/riscv-isa-manual/issues/2403) and
  [#3155](https://github.com/riscv/riscv-isa-manual/issues/3155) (ved-rivos: "SRET clears SDT unconditionally")
  disagree with [#2870](https://github.com/riscv/riscv-isa-manual/issues/2870) (aswaterman: the supervisor rule is
  qualified by S-mode, and SDT is preserved across a trap handled in M-mode), so that case is not checked.
  MRET and MNRET to S-mode and to VS-mode leave sstatus.SDT and vsstatus.SDT unchanged (#2403).
- With DTE=0, SDT may be cleared or masked on read ([#2264](https://github.com/riscv/riscv-isa-manual/issues/2264));
  either way the hart behaves as without Ssdbltrp, so SIE must still be settable
  ([#1623](https://github.com/riscv/riscv-isa-manual/issues/1623)).
- The stacking of SIE through SPIE is unaffected by SDT; only explicit CSR writes are
  ([#3057](https://github.com/riscv/riscv-isa-manual/issues/3057)).
- A VS-mode double trap goes to M-mode: medeleg[16] is read-only zero.
- DUT findings (`~/act-wt/dbltrp-findings.md`):
  - Spike: with DTE=0 after SDT was 1, SIE cannot be set (`menvcfg_dte_op`, [riscv-isa-sim#2534](https://github.com/riscv-software-src/riscv-isa-sim/issues/2534)); the fix for
    [riscv-isa-sim#2374](https://github.com/riscv-software-src/riscv-isa-sim/issues/2374) covers only the sstatus proxy.
  - Whisper: a trap into VS-mode does not set vsstatus.SDT, a VS trap with vsstatus.SDT=1 is not a double trap, and
    MRET/MNRET to VU leave vsstatus.SDT (`vsstatus_sdt_op`, `vsstatus_sdt_clr_*_Sm`; [whisper#238](https://github.com/tenstorrent/whisper/issues/238), fix in
    [whisper#240](https://github.com/tenstorrent/whisper/pull/240)); SRET is
    [whisper#228](https://github.com/tenstorrent/whisper/issues/228).
  - QEMU: RV32 henvcfgh accesses raise illegal instruction
    ([qemu#4611](https://gitlab.com/qemu-project/qemu/-/issues/4611)); mstatus.MPV is read-only zero
    ([qemu#4588](https://gitlab.com/qemu-project/qemu/-/work_items/4588)), so MRET never enters VS/VU.
