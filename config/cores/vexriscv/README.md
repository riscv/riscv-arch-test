# ACT Configuration for the VexRiscv Core

[VexRiscv](https://github.com/SpinalHDL/VexRiscv) is Charles Papon's in-order RV32 core, written in
SpinalHDL as a set of plugins on a 5-stage pipeline. This configuration runs the netlist LiteX uses
for `--cpu-type=vexriscv --cpu-variant=imac`, `VexRiscv_IMAC.v` from
[litex-hub/pythondata-cpu-vexriscv](https://github.com/litex-hub/pythondata-cpu-vexriscv) at
`642ecfe`, in a Verilator testbench of this repository (`.github/scripts/vexriscv-tb.cpp`).

| Config          | ISA                                         | Modes  |
| --------------- | ------------------------------------------- | ------ |
| `vexriscv-imac` | RV32IMAC_Zicsr_Zicntr_Zifencei_Zaamo_Zalrsc | M only |

- Privileged specification 1.11 (`Sm 1.11.0`): there is no `mstatush`, `menvcfg` or `mconfigptr`.
- 5-stage pipeline (fetch, decode, execute, memory, writeback) with full bypassing, single-cycle
  multiplier and divider plugins, barrel shifter, static branch prediction.
- 4 KiB direct-mapped instruction and data caches with 32-byte lines; the data cache is
  write-through. Addresses with bit 31 set are uncached I/O.
- No PMP, no `mcounteren`, `mcountinhibit` or `mhpmcounter` events (`mhpmcounter3`-`31` read 0).
- `time` is not implemented; ACT emulates it from the testbench's `mtime`.

## Generator configuration

The netlist is generated by `pythondata_cpu_vexriscv/verilog/Makefile` with

```
sbt compile "runMain vexriscv.GenCoreDefault --csrPluginConfig all --atomics true \
  --compressedGen true --outputFile VexRiscv_IMAC"
```

(SpinalHDL 1.9.4, from the VexRiscv sources in the repository's `ext/VexRiscv` submodule,
`b6118e5`). Every other `GenCoreDefault` option keeps its default: 4 KiB instruction and data
caches, `mulDiv`, `singleCycleMulDiv` and `singleCycleShift` true, `bypass` true, `prediction`
static, no debug plugin, no hardware breakpoints, no PMP, no CFU, `externalInterruptArray` true,
and no `resetVector` or `machineTrapVector` (the reset vector is the `externalResetVector` input,
and `mtvec` has no reset value). `--csrPluginConfig all` selects `CsrPluginConfig.all`: machine
mode only, `mvendorid`/`marchid`/`mimpid` = 11/22/33, writable `mcause`, `mtval`, `mcycle` and
`minstret`, readable `cycle` and `instret`, and `wfi` that waits for an interrupt.
`install-vexriscv.sh` downloads the checked-in netlist (its SHA-256 is pinned) and uses it
unchanged, so CI needs no JDK or sbt.

LiteX's Linux variants were not chosen: `--csrPluginConfig linux-minimal` (`VexRiscv_Linux`) makes
`mtvec` write-only and `misa` absent, so the ACT framework cannot install or restore its trap
handler. The `imac` variant is the most complete standard netlist that keeps the M-mode CSRs
readable and writable.

## Testbench

`.github/scripts/vexriscv-tb.cpp` models what a LiteX SoC gives the core:

- RAM: 256 MiB at `0x4000_0000` (LiteX's `main_ram` base; the tests must stay below bit 31,
  which is I/O). The testbench loads the ELF itself and drives `externalResetVector` to the RAM
  base.
- Wishbone: every beat is acknowledged one cycle after the request, with an idle cycle between
  beats (as LiteX's `wishbone.SRAM`), so a 32-byte cache refill takes 16 cycles.
- Console at `0xF000_0000`, exit register at `0xF000_0004` (the word written is the exit status).
- CLINT-style `msip` (`0xF001_0000`), `mtimecmp` (`0xF001_4000`) and `mtime` (`0xF001_BFF8`,
  writable, one tick every 10 cycles).
- `externalInterruptArray` at `0xF000_0008`. `RVMODEL_BOOT` sets bit 0 of the custom mask CSR
  `0xBC0`, which LiteX's interrupt code also programs, so source 0 raises `mip.MEIP`.
- No access faults. The netlist's Wishbone bridges ignore `ERR` and wait for `ACK`
  (`rsp.error := False` in `DataCache.toWishbone` and `InstructionCache.toWishbone`), so an
  access that only got `ERR` would hang, and the core has no PMA or PMP check. The testbench
  answers unmapped addresses with `ACK` and `ERR` and data 0, as LiteX's bus timeout does, and
  `rvmodel_macros.h` leaves `RVMODEL_ACCESS_FAULT_ADDRESS` undefined.

## Configuration notes

The UDB feature extractor (riscv-arch-test #2442) was run on the testbench; the yaml differs
from what it reports where a directed probe or the source shows the extractor was misled:

- `U` is not claimed: `mstatus.MPP` cannot be written to 0, and after `mret` the hart is still in
  M-mode (`mscratch` is accessible and `ecall` reports cause 11). The extractor saw `MPP` read 0
  after an `mret`, which is a core bug (below).
- `Zcb` and `Zcmop` are not claimed: their encodings are reserved here. The decompressor executes
  some of them as other instructions (`c.not` as an AND, `c.mul` as an OR, `c.mop.1` as
  `c.lui x1, 0`) instead of raising an illegal-instruction exception, so the extractor's probe saw
  no trap.
- `Zihpm` is not claimed: `hpmcounter3`-`31` read 0, but only from M-mode.
- `NUM_PMP_ENTRIES` is 0: `pmpcfg*` and `pmpaddr*` read 0 and ignore writes.
- `MTVEC_ILLEGAL_WRITE_BEHAVIOR` is `custom`: a write with MODE 1 or 3 sets BASE and leaves MODE 0,
  which Sail's `Xtvec_Ignore` models.
- `TRAP_ON_EBREAK` is true although `ebreak` raises an illegal-instruction exception (below): UDB's
  false means a transparent `ebreak` without any trap.
- `Zicntr` is claimed with `TIME_CSR_IMPLEMENTED: false`.

Sail cannot model the data cache's reservation, a single bit that any `sc` to any address
consumes; `sail.json` uses the largest reservation set Sail accepts (4 KiB). The two agree only
while an `lr` and the `sc` after it fall in the same 4 KiB block. The Zalrsc test for
`sc_pairs_latest_lr` (an `lr` to `scratch`, an `lr` to `scratch + 256`, then an `sc` to `scratch`)
passes because `scratch` is 256-byte aligned and is not at page offset `0xF00`; at that offset the
second `lr` would reserve the next block, Sail would make the `sc` fail, and VexRiscv would
let it succeed.

## Excluded tests (`ci.yaml`)

Each is a deviation from the specification in this netlist:

- `ebreak` and `c.ebreak` raise an illegal-instruction exception: `CsrPluginConfig.all` leaves
  `ebreakGen` false, and the generator warns about it.
- `mepc[0]` is writable.
- A write to a read-only CSR (`cycle`, `mvendorid`, ...) does not trap.
- `ecall` writes its encoding to `mtval`, and an interrupt leaves `mtval` unchanged; both must
  write 0.
- `mret` sets `mstatus.MPP` to 0 although U-mode is not implemented.
- A `csrw minstret` is followed by the write's own increment, so `minstret` reads one higher than
  written.

Also not tested but non-conforming: `misa` reads `0x4000_0042` (B and G set, I, M, A and C clear).
