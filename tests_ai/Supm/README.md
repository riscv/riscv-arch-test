# Supm: rule-derived tests for U-mode pointer masking

Supm only says that U-mode has pointer masking with "some facility" of the application execution environment to
control it. These tests run in the lowest mode (U) and use T-SBI writes of senvcfg.PMM (menvcfg.PMM on harts without
S) as that facility; `pm_ignore_upper_bits` requires that it can enable masking. Generated by `gen/gen_Spm.py`; the shared mechanics are in `../Smnpm/README.md`.

## How the extension is tested

- `pm_ignore_upper_bits`, `pm_ignore_pa`: Bare (physical) accesses with tags and every PMLEN boundary bit.
- `pm_apply_explicit`: every class of explicit access from U-mode.
- `pm_not_apply_implicit`: fetches from tagged addresses fault.
- `pm_misaligned_equivalence`: within-page and page-crossing misaligned accesses.
- `pm_mxr_exception`: MXR=1 (sstatus through T-SBI; read back, since it is read-only zero without S) disables masking.
- `pm_ignore_va_Sm`: U-mode under satp Sv39/Sv48/Sv57 with user pages. U code needs user pages but the S-mode trap
  handler needs supervisor ones, so this part boots to M-mode (traps from U go to M) and requires Sm and S.

## Rules not tested here

- U-mode has no address CSRs, so `pm_no_csr_sw`, `pm_warl_unaffected` and `pm_csr_hw_apply` are in Sspm/Smmpm.
- RVA23U certification gets no U-mode virtual-address test: `pm_ignore_va_Sm` needs Sm (see above).
- See `../Smnpm/README.md` for the rest.

## Subtleties

- On harts without S (MU), menvcfg.PMM controls U-mode and MXR is read-only zero, so the MXR test expects masking.
