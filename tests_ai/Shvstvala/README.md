# Shvstvala: rule-derived tests for vstval

One test for the only `norm:` rule in `src/priv/shvstvala.adoc`: vstval is written in every case that Sstvala
describes for stval. Generated by `tests_ai/gen/gen_Sx.py`. Mutants are named `Sx:vstval_*`.

## How the extension is tested

- **Delegation to VS-mode.** hedeleg sends causes 0, 1, 2, 4-7, 12, 13 and 15 to VS-mode. ecalls stay with HS-mode
  for T-SBI. hgatp is Bare.
- **Cases**, each checked to be taken by the VS handler with the exact vstval:
  - misaligned loads and stores from VS and VU, and an access fault at `RVMODEL_ACCESS_FAULT_ADDRESS`;
  - illegal instructions from VS and VU, and C.FLDSP with `vsstatus.FS`=Off;
  - instruction-address-misaligned from VS on harts without C;
  - with vsatp Sv39 or Sv32 (probed) and a VS-stage identity map of the image, VS-mode code takes page faults,
    straddling accesses, an access fault through a page mapped onto the fault address, and a 32-bit instruction
    whose second half is in an invalid page.

## Rules not tested here

- VU-mode page faults: VU code would need a second, U=1 VS-stage view of the image. The VS-mode paging cases and the
  VU Bare cases cover vstval.
- Breakpoints that write an address (Sdtrig triggers in VS-mode) are not programmed.

## Subtleties

- Virtual-instruction exceptions are never taken in VS-mode, so no vstval case exists for them.
- On configurations with the invisible trap handler, illegal instructions from VS reach VS-mode through M-mode,
  which writes vstval itself.
