=== Pipeline Hazard Tests

This appendix describes the architecture of the cp_gpr_hazard and
cp_fpr_hazard coverpoints and their associated test generators.

==== Hazard Types

Three classes of pipeline data hazards are relevant to RISC-V certification:

* RAW (Read-After-Write): A consumer instruction reads a register before
  the producer write has retired. The pipeline must forward the correct
  value to the consumer. This is the primary hazard class tested.
* WAW (Write-After-Write): Two instructions both write the same destination
  register. The second write must win. Relevant for multi-cycle instructions.
* WAR (Write-After-Read): Register WAR is not a real hazard in an in-order
  pipeline, because the read completes before the write in the same stage.
  Memory WAR (a store followed by a load of the same address) tests
  store-to-load forwarding and is not yet implemented.

==== Generator Architecture

The generator uses a Category x Category approach: every consumer instruction
category is tested against a selected producer. The instruction named by the
testplan row is always the consumer, because a covergroup only samples when
its own instruction retires; a hazard in which that instruction were the
producer would be attributed to a different covergroup.

===== Producer Selection

For RAW the producer is always add. A single-cycle producer isolates the
consumer bypass path from producer-dependent pipeline variance.

For WAW the producer is chosen by latency. A single-cycle producer cannot
expose a WAW bug against a multi-cycle consumer: the producer always
completes first, so "last write wins" holds by construction and no
implementation can fail. Where the consumer is materially faster than the
slowest available operation, the generator substitutes a long-latency
producer so that the consumer retires first, making the ordering requirement
observable.

[cols="2,2,3"]
|===
|Consumer|WAW Producer|Rationale

|mul, mulh, mulhsu, mulhu, mulw
|div
|Consumer latency is well below div, so the consumer retires first.

|div, divu, rem, remu and word variants
|add
|Consumer latency matches div, so a div producer would not stress ordering.

|fadd.s, fsub.s, fmul.s, fmin.s, fmax.s, fsgnj[n,x].s, fmadd.s, fmsub.s,
 fnmadd.s, fnmsub.s
|fdiv.s
|Consumer latency is well below fdiv.s.

|fdiv.s, fsqrt.s
|fadd.s
|Consumer latency matches the long-latency producer.

|All other instructions
|add or fadd.s
|Single-cycle consumers; no latency mismatch to exploit.

|===

The multi-cycle consumer sets are currently enumerated by instruction name
because the framework carries no instruction latency model.

===== Depth

Depth=n means there are n instructions between the producer and consumer.

* Depth=0: Consumer immediately follows producer. Tests basic bypass.
* Depth=1: One filler instruction separates them. Tests forwarding across
  a pipeline stage boundary.

Depth=0 and Depth=1 are the certification core. Depth greater than 1 is
not implemented and requires investigation of RVVI retirement buffer capacity.

===== Filler Classes

Depth=1 tests use two filler classes, each exposing a distinct failure mode:

* Class A NOP (addi x0, x0, 0): Catches a broken basic bypass path.
* Class B Structural stressor: An independent instruction on the same
  functional unit using registers disjoint from both producer and consumer.
  Catches pipelines that track the last result from the FU rather than the
  last write to the specific register. Stressor registers are explicitly
  excluded from overlapping with the producer destination or the consumer
  sources, for both the integer and floating-point register files.

A third class, an always-not-taken branch to detect forwarding state being
flushed on branch decode, is not implemented.

===== Source Port Coverage

RAW tests exercise each source port separately. Integer coverpoints provide
raw_rs1_depth0, raw_rs2_depth0, raw_rs1_depth1 and raw_rs2_depth1 bins.
Floating-point coverpoints additionally provide raw_fs3 bins for the
four-operand fused multiply-add forms. Port identity is resolved by
check_gpr_hazard_field() and check_fpr_hazard_field(), which return which
source port matched the producer destination.

Coverage bin names match the generated test case names, except that the two
depth=1 filler classes (nop and stressor) both map to the single
raw_*_depth1 bin.

===== WAW Tests

WAW tests place a producer and the consumer both writing the same destination
register. The consumer result must win. SIGUPD is placed on the consumer.
Operand values are randomly generated, so a WAW failure is detected whenever
the two instructions compute different results; no explicit constraint
currently forces the values apart.

==== Test Budget

Each instruction currently generates seven hazard test cases: RAW on each
available source port at depth=0, the same ports at depth=1 with each of the
two filler classes, and one WAW case. This is well within the
100-test-per-instruction cap, leaving room for the unimplemented items above.
