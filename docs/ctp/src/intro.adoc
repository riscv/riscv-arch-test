
== Introduction

This Certification Test Plan describes the RISC-V Architectural Certification Tests (ACTs) for ratified extensions, including those needed to certify a Device Under Test (DUT) implementing RISC-V profiles. It summarizes the profiles intended to be supported and the test suites that need to run for each profile.  It describes the overall ACT design strategy and requirements for ACT tests.  The Test Supervisor Execution Environment (T-SEE) and Test Supervisor Binary Interface (T-SBI) abstract machine-mode services for profiles that do not specify machine mode requirements.  Functional coverage is adapted from riscvISACOV using architectural state updates communicated via the RISC-V Verification Interface (RVVI). Tests are self-checking, using expected values provided by a reference model during 2-pass compilation. The appendices provide test plans and normative rule mappings for each unprivileged, privileged, and non-ISA extension.

=== Certificates and Certification

A RISC-V _Certificate_ is a named set of requirements for a RISC-V implementation, typically defined by a ratified profile. For example, the RVA23 Certificate requires meeting the RVA23S64 profile.

_Certification_ is the process of testing that a RISC-V implementation meets the requirements of a RISC-V certificate.  The goal of certification is to deliver software interoperability across implementations.  Overall, the ACTs are intended to promote similar interoperability for code using any extension, not just those in a profile.

There is a fuzzy line between certification and verification.  Certification involves testing that an implementation meets all of the normative rules in ratified specifications relevant to the certificate, but does not involve testing that requires detailed knowledge of the microarchitecture. Specifically, certification does not check timing (such as the arrival of interrupts relative to the start, middle, or end of multicycle instructions), deep pipeline hazards, power management features, etc.

Certification assumes the ratified specification is read and interpreted with knowledge of computer architecture and reasonable judgement, because not every detail is spelled out in normative rules.  For example, certification that "ADD performs the addition of _rs1_ and _rs2_" involves testing ADD with a reasonable set of values.  The test plan author exercises judgement selecting these values because they are not spelled out.  For example, the values might involve every combination of {0, 1, -1, maximum positive integer, maximum negative integer, intermediate value} for the two source register values. The intermediate value involves an arbitrary choice.  Another reasonable author might pick some other sensible edge values, such as some values one more or less than those in the set above.  However, certification does not attempt to prove every bit of a carry chain works for every possible input, or that all stuck-at faults would be detected. Similarly, the test plan author may exercise all 32 registers as sources or destinations for each instruction, which is implicitly required but not spelled out in a normative rule.

When in doubt, it is better to test slightly more than strictly necessary for normative rules, rather than slightly less. Over-testing is acceptable, as long as it does not cause false failures or excessive test time. It is often easier to test cross-products of all relevant inputs, even if not all combinations are explicitly named by normative rules. It also reduces the risk of human error missing a required combination.

The certification process involves more than just passing tests.

=== Test Supervisor Execution Environment (T-SEE) and Test Supervisor Binary Interface (T-SBI)

Ratified profiles specify supervisor and user mode and impose very few requirements on machine mode.  For example, RVA23S64 does not require the Sm1p13 machine mode described in the RISC-V Privileged Architecture Manual. A DUT could add fields to `mstatus`, add or delete CSRs, or completely change the machine mode behavior.  This significantly complicates testing because the tests cannot rely on ratified machine mode to do things like boot the DUT, delegate traps, handle invisible traps, manage counters, or access protected memory regions such as for an interrupt controller. These machine mode services take place in the Test Supervisor Execution Environment (T-SEE).  Tests running at the supervisor or lower mode use the Test Supervisor Binary Interface (T-SBI) to request services from the T-SEE, such as accessing privileged memory regions or CSRs. The T-SBI is described further in <<t-tsbi,T-SBI>>.

riscv-arch-test provides a reference implementation of boot code, trap handlers, and T-SBI compatible with the machine mode described in the RISC-V Privileged Architecture Manual. A DUT that implements Sm1p* or a nearly-compatible machine mode can use this reference implementation.  A DUT with significantly different machine mode may need to reimplement some or all of the reference implementation to run the tests.  This could be a costly undertaking because of the subtle nature of this code.

=== Test Suites, Normative Rules, Coverpoints, Test Plans, and Tests
The ACTs are organized by _test suites_.  There are test suites for the base I and E ISAs, suites for each ratified extension (including Sm machine mode, S supervisor mode, U user mode, and H for HS/VS/VU and all other features added by hypervisor), and suites for a few features that cross extensions: Exceptions, Interrupts, PMP, etc.  Most test suites tie to specific chapters of the ISA manual, but some touch on rules spread across multiple chapters.  Certification testing runs all of the test suites that apply to the extensions in the profile being certified.

Normative rules are the key to certification.  Normative rules are tagged portions of the ratified ISA manuals. They list the requirements of the RISC-V architecture that need to be tested in order to certify a profile. However, normative rules are human-readable portions of a specification and cannot be checked in an automated manner.

Instead, the test plan maps normative rules to coverpoints, which are machine-readable descriptions of the conditions to be exercised. Hitting a coverpoint establishes that a condition was exercised; the associated test must also check the required architectural behavior. Not all normative rules have tests or coverpoints; exclusions and coverage gaps are documented in the test plan and normative rule mappings.

Each coverpoint has a set of tests that exercise it, and each test has a set of coverpoints that it hits.

This test plan identifies normative rules applicable to each extension, specifies coverpoints for the conditions under test, and outlines tests that exercise those conditions and check the results. The tests are self-checking and report pass/fail results. Coverage reports show which applicable coverpoint bins were hit and which remain uncovered. Test results and coverage together provide evidence for the mapped rules; coverage alone does not establish correct behavior.

Coverpoints are written in SystemVerilog, and are designed to be used with the Extended https://github.com/riscv-verification/RVVI[RISC-V Verification Interface] (RVVI).  They are written to be independent of the DUT, so that they can be used with any RISC-V implementation. footnote:[Extended RVVI adds signals for virtual memory verification, including physical and virtual instruction and data addresses, and I/D TLB entries.] Functional coverage is collected using SystemVerilog infrastructure adapted from https://github.com/riscv-verification/riscvISACOV[riscvISACOV] footnote:[Portions of riscvISACOV that depend on proprietary Synopsys code such as a disassembler have been replaced with open-source equivalents].

Coverpoints are organized into .svh SystemVerilog coverage files, each of which contains one or more covergroups, each of which contains one or more coverpoints.  Coverage files apply to a DUT with a particular set of extensions.  For example, the I_coverage.svh coverage file is used for any 32 or 64-bit DUT that supports the I extension. Some covergroups in a coverage file apply only when another extension is also supported; for example, the half-double conversion covergroups in Zfh_coverage.svh are compiled only when D is supported. Thus, a coverage file is organized by covergroups that may rely on a combination of extensions or parameters.  Unprivileged test suites have one covergroup per instruction.  For example, the Zcb test suite contains covergroups for `c.lbu` and `c.mul`.  The `c.mul` covergroup only applies to DUTs that also support Zmmul (which M implies). Privileged test suites usually have one covergroup per combination of extensions or parameters, such as `Sstc`, `Sstc_H`, `Sstc_Sm`, and `Sstc_HSm`. Covergroups including `Sm` are only applicable to DUTs that support standard machine mode and are not part of RVA23 certification.

Tests are written in assembly language or C. Tests are organized into directories for each extension, and into a privileged directory.  The coverpoints are hit by running all of the applicable tests in a directory.  For example, RV32I coverage involves running `I-add-00.S`, `I-addi-00.S`, `I-sub-00.S`, and any subsequent numbered chunks under `tests/rv32i/I/`.  RV64I coverage also involves running `I-addw-00.S` under `tests/rv64i/I/`, which is unique to RV64.  Each file begins with a TEST_CONFIG block that specifies the required extensions and parameters for the tests in that file. When compiling tests for a particular DUT, only those applicable to the DUT's extensions and parameters are built.

The test suite is too large to hand-code in assembly.  Instead, the assembly is produced by Python generators.  Unprivileged generators automatically produce tests and coverpoints based on a comma-separated value (CSV) test plan specifying which coverpoints apply to which instructions.  Privileged test generators and coverpoints are written based on human-readable YAML test plans.

=== Glossary

The following terms are used in this test plan:

* Extensions: named and ratified RISC-V extensions, such as RV32I, M, Zbb, Zicsr, or Svadu.  Many extensions define instructions or CSRs, but some only define parameters (e.g. Sstvecd requires that STVEC_MODES includes 0).

* Parameters: options describing the behavior of extensions.  All parameters will be named by the Parameters Working Group (started February 2026) and will appear in UDB. For example, the PMP_GRANULARITY parameter defines the minimum size of a
PMP region.

* Configuration: A set of extensions and parameters partially or fully describing the behavior of a RISC-V hart.  A full configuration is sufficient for a reference model to exactly match the behavior of a DUT except with regard to non-deterministic behaviors. Configurations are described in machine-readable YAML format that are read by UDB and used to generate configuration files for various tools.

* Constrained Non-Deterministic Behaviors: behaviors whose exact result cannot be predicted from architectural configuration or defined parameters, but whose legal outcomes are restricted by the specification. For example, each tail-agnostic vector destination element may retain its previous value or be overwritten with all ones, in any combination within a single instruction. Mask destination tails have additional permitted outcomes, including values computed by the mask-producing operation under the conditions specified by the vector ISA. The DUT and reference model therefore need not produce identical results. Self-checking tests must accept all legal outcomes for non-deterministic behaviors.

* Unconstrained Non-Deterministic Behaviors: behaviors that cannot be predicted based on either architectural configuration or defined parameters, and whose result is not constrained to a small number of possible values.  For example, the value of an integer register after reset is an unconstrained non-deterministic behavior.  Tests must not make any assumptions about the value of such behaviors, and must not check them against the reference model.

* Profile: A named collection of required and optional extensions, such as RVI20 or RVA23S64.  Profiles may be ratified by RISC-V or developed by the Certification Steering Committee to meet certification market needs, such as a simple microcontroller. A profile is a partial configuration.  The test plan must allow the DUT configuration to indicate which optional extensions and other parameters are used, and fully test all optional profile extensions provided by the DUT.

* UDB: https://github.com/riscv/riscv-unified-db[Unified Database], a standardized way to describe the configuration and generate config files for various tools from a single point of truth.

* <<Normative Rules,Normative rule>>: A named direct quotation from a ratified specification, describing a single certifiable feature.

* Coverage files: a SystemVerilog .svh file containing all of the covergroups for an extension or combination of extensions, such as I_coverage.svh or ZfaD_coverage.svh.

* Covergroup: A SystemVerilog construct that contains one or more coverpoints.  Covergroups are used to collect functional coverage of a particular feature or set of features in the RISC-V architecture.  For example, the I_coverage.svh file contains a covergroup for each instruction in the I extension, such as add, addi, sub, etc.  The Exceptions_coverage.svh contains covergroups such as Exceptions_S_cg, Exceptions_F_cg, and Exceptions_HSm_cg.

* Coverpoint: A SystemVerilog construct describing a set of conditions to test.  For example, the cp_rd coverpoint checks that all 32 destination registers x0-x31 are exercised by instructions that don't trap. Each coverpoint has one or more bins; for example, cp_rd has 32 bins for the different registers.

* Bin: One target value for a coverpoint.  Each bin may be covered or not by a test suite.  A complete test suite should cover all bins applicable to a DUT.

* Test files: A file containing one or more tests, typically written in assembly language.  For example, `tests/rv32i/I/I-add-00.S` contains a chunk of the RV32 tests for the `I_add_cg` covergroup in `coverpoints/unpriv/I_coverage.svh`. Additional chunks use consecutive numeric suffixes.

* Test: A snippet of code, typically a sequence of assembly language instructions, that exercises at least one bin of a coverpoint.

* Test Suite: A collection of coverage and test files to test a particular extension, base ISA, or other major feature (e.g. Exceptions).  Also includes a test plan and a mapping of normative rules to coverpoints.

* RVMODEL DUT-Specific Macros: A set of macros that perform _semihosting_/_trick box_ functions such as booting the DUT, sending interrupts, and logging results. The macros are defined in <<rvmodel-macros, RVMODEL DUT-Specific Macros>>.
