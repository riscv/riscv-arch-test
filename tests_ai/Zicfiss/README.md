# Zicfiss: rule-derived tests for shadow stacks

One test per `norm:` rule about Zicfiss: the Zicfiss part of `src/unpriv/cfi.adoc` and `src/priv/cfi.adoc`, the SSE
fields of `menvcfg` (`machine.adoc`), `senvcfg` (`supervisor.adoc`) and `henvcfg` (`hypervisor.adoc`), and the
shadow-stack code of the software-check xtval lists. Generated by `tests_ai/gen/gen_Zicfiss.py`, with helpers in
`gen/zicfisslib.py` (encodings, SSE enables, S-level paging with a U alias) and `gen/hmem.py` (page tables).

## How the extension is tested

- **Modes.** Tests boot to S-mode and set `menvcfg.SSE` through T-SBI and `senvcfg.SSE`/`henvcfg.SSE` directly.
  `<rule>_Sm.S` files boot to M for M-mode behavior (ssp and ssrdp in M, M-mode and MPRV `ssamoswap`, software checks
  taken in M with `medeleg[18]=0`) and require `Sm`. VS and VU parts are under `#if defined(H_SUPPORTED)` or in files
  that require H.
- **Encodings.** Zicfiss instructions, AMOs, LR/SC and CBOs are `.word`/`.hword` encodings, so MARCH stays
  `rv${XLEN}i_zicsr_zifencei` and the encodings are the legal xtval of illegal/virtual-instruction traps. Compressed
  forms are followed by `c.nop` and run under `ZCMOP_SUPPORTED`.
- **Paging.** Shadow-stack accesses need translation, so memory tests build an Sv39 (RV64) or Sv32 (RV32) table: the
  image identity mapped without U, test pages at constant VAs, and the code mapped a second time with U=1 and
  registered as the S save area's code alias, so U-mode runs there through `RVTEST_TSBI_GOTO_UMODE`. The satp MODE is
  probed by writing it; a hart without it skips the paged part. VS-mode tests use vsatp (hgatp Bare), and
  `active_g_stage_pte` uses both stages (Sv39x4/Sv32x4 probed). Memory contents are checked untranslated through
  T-SBI loads, so a test never relies on the behavior it checks to read its result. Low memory below the test pages
  is identity mapped (RW, no X/U) so the framework's failure reporter can reach MMIO devices while the map is on.
- **Traps.** Every trap is checked in the trap log: count, cause, xepc (the U-alias address for U-mode, the target
  for fetch faults), xtval (0 or the address for memory faults; 0 or the instruction bits for illegal/virtual
  instruction; exactly 3 for a shadow-stack software check, with stval/mtval preset to another value), the mode the
  trap came from and, for guest-page faults, htval, GVA and htinst. After faulting shadow-stack instructions, ssp, rd
  and memory are checked unchanged.
- **Outcome sets.** Misaligned `ssamoswap`: address-misaligned or access fault. `sc.w` to an SS page: access fault or
  a failed SC that writes nothing. RV64 ssp bit 2: probed (`mstatus.UXL` decides whether it must be writable), and
  `ssp_xlen_aligned` runs only when it is.
- **Mutation check.** `MUTANTS` in the generator lists 45 expectation flips (for example sspopchk faults reported as
  load faults, ssp moved on a faulting push, VU-mode ignoring henvcfg.SSE, an ordinary store to an SS page giving a
  page fault). Each makes a test fail on Sail, except `misaligned_ssp_ok`, which needs a hart with a writable ssp
  bit 2 (see below).

## Rules not tested, or only partly

- **No configuration selects the test:** `Zicfiss_smode_xsse_Sm` needs a hart with Zicfiss but no S-mode
  (`FORBIDDEN_EXTENSIONS: [S]`); no ACT configuration has one.
- **Reachable only on some harts:** `ssp_xlen_aligned` needs RV64 with a writable ssp bit 2 (on RV32 bits 1:0 are
  read-only zero, so ssp is always XLEN aligned). Sail rv64 makes bit 2 read-only zero, so the file passes trivially
  there and its mutant survives.
- **Partly:**
  - `ssmp_ss_idempotent_memory`: non-idempotent memory is reached only through Svpbmt PBMT=IO (RV64). Non-idempotent
    PMA regions are platform-specific.
  - `ssmp_ss_implicit_access_fault`: instruction fetch only, the one implicit access subject to S-stage translation.
  - `henvcfg_sse_op` and `ssmp_henvcfg_sse`: the reserved VS-stage encoding is checked from VS-mode, not VU-mode (a VU
    code alias in the VS-stage map is not built).
  - `active_g_stage_pte`: VS-mode only, explicit accesses only (not guest-page faults on the VS-stage table walk).
  - `ssp_field_1_0`: on RV64 with UXL fixed at 64, bit 2 may read 0 or 1 (SXL is not probed from S-mode, and the
    rule's "UXLEN or SXLEN may never be 32" is read as "neither can be 32"; a spec clarification would help).
  - Store classes in `ssmp_ss_page_access_fault`: base stores, Zaamo AMOs and Zalrsc SC (S and U); compressed and FP
    stores, and V=1, are not covered. Loads in `ssmp_ss_load` likewise cover base loads and LR.
  - MPRV with MPV=1 (effective V=1) is not covered.
- **Covered inside another file:** `mtval_swchk_lead_in` and `stval` lead-ins are the first sentence of the list
  rules (`mtval_swchk_list_Sm`, `stval_exception_info`); the code-2 (landing pad) entries belong to Zicfilp.
- **Untagged text, not tested:** PMP read-write requirement for shadow-stack accesses, the AMOSwap PMA requirement of
  `ssamoswap`, Svnapot SS pages, and the note that changes to xSSE need no `sfence.vma` (tests fence after each
  change).
- **Other suites:** the grep for `SSE|ssp|shadow` over `src/priv` also matched Zicfilp (`cfi_*spelp*`), Zkr
  (`mseccfg_sseed*`), counters (`*_op_rdonly` "shadows"), Svpbmt, PMA and pointer-masking rules; they are not Zicfiss
  rules.

## Subtleties

- VU-mode with `henvcfg.SSE=0`: `senvcfg.SSE` is read-only zero while V=1, so VU-mode sees Zicfiss inactive (ssrdp
  writes 0, ssp access and ssamoswap raise virtual-instruction) even when HS-mode set `senvcfg.SSE`
  ([#2424](https://github.com/riscv/riscv-isa-manual/issues/2424)).
- With `menvcfg.SSE=0`, ssp access from VS/VU is illegal-instruction, not virtual
  ([#2708](https://github.com/riscv/riscv-isa-manual/issues/2708)).
- Whether xwr=010 is reserved depends on `menvcfg.SSE` (and `henvcfg.SSE` when V=1), never on `senvcfg.SSE`
  ([#2449](https://github.com/riscv/riscv-isa-manual/issues/2449)).
- An ordinary store to an SS page is an access fault even when D=0: the shadow-stack check precedes the A/D step
  ([#2380](https://github.com/riscv/riscv-isa-manual/issues/2380)).
- `ssamoswap` follows the current privilege for its enable checks, and the effective privilege (MPRV) for the
  access; in M-mode the access faults ([#2408](https://github.com/riscv/riscv-isa-manual/issues/2408),
  [#2420](https://github.com/riscv/riscv-isa-manual/issues/2420), [#2461](https://github.com/riscv/riscv-isa-manual/issues/2461)).
  sspush/sspopchk are MOPs in M-mode even with MPRV=1 ([#1534](https://github.com/riscv/riscv-isa-manual/issues/1534),
  [#2467](https://github.com/riscv/riscv-isa-manual/issues/2467)).
- The misaligned atomicity granule does not apply to `ssamoswap`
  ([#3425](https://github.com/riscv/riscv-isa-manual/issues/3425), PR #3426).
- `ssamoswap` writes rd last, so rd may alias rs1 or rs2 (PR #3433).
- After `henvcfg.SSE` changes, VS-mode's view of `senvcfg.SSE` may be UNSPECIFIED (field modulation), so HS-mode
  writes `senvcfg.SSE` again before VS-mode reads it.
- Guest-page faults on the explicit access of sspush/sspopchk write htinst = 0; ssamoswap may write the transformed AMO
  ([#1935](https://github.com/riscv/riscv-isa-manual/issues/1935), [#2477](https://github.com/riscv/riscv-isa-manual/issues/2477)).
- sspopchk faults are store/AMO faults (15, 7, 23), and the software check ranks below an access fault.
