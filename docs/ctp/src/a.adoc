The spec imposes no requirements on reservation set form, including alignment, NAPOT, or even being contiguous.  Therefore, it is not practical to build reference models that reliably predict whether a `sc` would succeed or fail on every DUT.  Current profiles require Za64rs or Za128rs, which can be supported by reference models. However, unusual DUTs that do not match any reasonable reference model may not be able to pass this test suite. The expected outcome of an `sc` to an address other than that of the latest `lr` but within its reservation set follows the LRSC_RESERVATION_STRATEGY and LRSC_FAIL_ON_NON_EXACT_LRSC parameters.

The `sc` tests follow these conventions:

* An `sc` may fail spuriously, so every testcase that expects an `sc` to succeed runs the `lr`/`sc` pair in a constrained LR/SC loop (<<sec:lrscseq>>) that retries up to 100 times. If _rd_ is also _rs1_ or _rs2_, the loop restores that register from a copy before each attempt, because a failing `sc` overwrites it with the failure code. When _rd_ is `x0`, the `sc` reports no status, so the loop reads back the target to decide whether to retry. That load takes the loop out of the constrained form, but the loop is still bounded.
* Before each `sc`, the XLEN-bit word at the target is filled with the complement of _rs2_, so the `sc` changes every bit it writes. The test reads the target back afterward, so an `sc` that reports success but drops its store or writes another address fails, as does an `sc` that reports failure but writes memory.
* A failing `sc` is checked for _rd_ = 1. The other nonzero failure codes are reserved.
* cp_custom_sc_after_sc executes `lr`, then an `sc` to the address 8 bytes above, whose outcome is not checked, then an `sc` to the `lr` address. That second `sc` must fail and leave its target unchanged, whether or not the first one succeeded.
* The cp_custom_sc_addresses testcases and the testcase for sc_pairs_latest_lr make a single attempt, because their `sc` is either expected to fail or is outside a constrained loop.
* The suite does not deliberately place compressed instructions in its constrained loops, so constrained_lrsc_compressed_allowed is not tested.
