- Same base environment as ZicfissU, but tests execute in S/HS-mode. menvcfg.SSE alone gates S/HS; senvcfg.SSE does NOT gate S/HS. +

| Verify ssp CSR accessibility from S/HS-mode depends only on menvcfg.SSE, not senvcfg.SSE

| cp_ss_page_enc_zicfiss
| Verify the pte.xwr=010 encoding is recognised as an SS page, and is reserved when SSE is off
| With menvcfg.SSE=1 build a PTE with R=0, W=1, X=0 and use it as a shadow stack from S-mode and U-mode (SSPUSH then SSPOPCHK round trip, plus an ordinary load). +
Repeat with menvcfg.SSE=0.

| cp_ss_page_perm_priority_zicfiss
| Verify U, SUM and MXR permission checks on a shadow stack page, and that they outrank the SS access-fault rule
| The shadow stack page is R=0 and may be U=0 or U=1, so the ordinary permission machinery and the Zicfiss-specific rules can both apply to the same access. This coverpoint establishes which wins. +
Sweep, from S/HS-mode, the shadow stack page's U bit = 0/1 against sstatus.SUM = 0/1 and sstatus.MXR = 0/1, for: +
(a) every SS instruction that accesses memory (SSPUSH, C.SSPUSH, SSPOPCHK, C.SSPOPCHK, SSAMOSWAP.W/D); +
(b) an ordinary load from the same page, which is permitted by the shadow stack rules but still subject to U/SUM/MXR; +
(c) an ordinary store, which the shadow stack rules forbid regardless. +
Include the case where the permission check and the SS rule would produce DIFFERENT causes, so the priority is observable rather than coincidental.
| The U/SUM/MXR permission check is part of address translation and therefore resolves BEFORE any Zicfiss-specific rule. Where the two disagree, the translation fault is reported: +
U=1, SUM=0, access from S-mode -> page-fault from the U/SUM check, NOT the SS store/AMO access-fault, even for an instruction the SS rules would also have rejected. +
U=0, access from S-mode -> permitted by U/SUM; the SS rules then apply normally. +
MXR governs whether the R=0 shadow stack page is readable by an ordinary load. Per [norm:ssmp_ss_load] the shadow stack is readable by any load-only instruction, so this must hold for BOTH MXR values -- an implementation that requires MXR=1 to read an SS page is wrong. +
SS instructions themselves are unaffected by MXR: their access is a store/AMO-flavoured access, not a load.
| pte.U {0,1} x sstatus.SUM {0,1} x sstatus.MXR {0,1} x accessor {SS instr, ordinary load, ordinary store} x cause {none, page-fault from U/SUM, 7, 15} x priority {translation check wins}
| ssmp_ss_load ssmp_ss_page_access_fault ssmp_ss_page_illegeal_access ss_fault_exception_code
| [norm:ssmp_ss_load] [norm:ssmp_ss_page_access_fault] [norm:ssmp_ss_page_illegeal_access] [norm:ss_fault_exception_code]

| cp_senvcfg_sse_rdonly0_s_zicfiss
| Verify senvcfg.SSE reads back 0 from S-mode whenever menvcfg.SSE is 0
| Direct observation of the read-only-zero rule from the mode that owns senvcfg, rather than inferring it from an ssp access. +
From M-mode set menvcfg.SSE=0. Drop to S-mode and attempt to write senvcfg.SSE=1 using csrw, csrs and csrrw, reading the CSR back after each write. +
Repeat the same sequence with menvcfg.SSE=1 as the positive control. +
This is the S-mode counterpart of cp_envcfg_sse_rdonly0_zicfiss on the ZicfissSm sheet, which drives the same field from M-mode.
| menvcfg.SSE=0: senvcfg.SSE reads back 0 after every write attempt. No exception is raised -- SSE is a WARL field, so the write is discarded rather than rejected. +
menvcfg.SSE=1: senvcfg.SSE is writable and reads back what was written. +
This is what makes the (menvcfg.SSE=0, senvcfg.SSE=1) combination architecturally unreachable wherever it appears as a bin on this sheet or on ZicfissU.
| menvcfg.SSE {0,1} x csr_op {csrw, csrs, csrrw} x written {0,1} x senvcfg.SSE readback {0 when menvcfg.SSE=0, written when menvcfg.SSE=1}
| menvcfg_sse_rdonly0
| [norm:menvcfg_sse_rdonly0]
