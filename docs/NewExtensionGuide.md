

# Contributing ACT Test Cases for a New Extension: A Complete Guide from Freeze to Ratification

> This document is intended for community contributors. It consolidates the full set of deliverables, technical bars, and recommended cross-repository merge order for submitting a test-case pull request to the RISC-V Architectural Compatibility Test suite (riscv-arch-test, hereafter ACT / ACT4) on behalf of a not-yet-ratified extension such as Sspmp, Sspmpen, Smpmpdeleg, or Zvabd. Its purpose is twofold: to provide contributors with a coherent, one-shot preparation checklist, and to offer reviewers a clear, uniform set of review anchors.



## 1. Overview

ACT4 is the official RISC-V architectural compatibility test suite. Its core workflow can be summarized as follows: 
```
tagged normative rules in the specification
   ↓
coverpoints
   ↓
testplan
   ↓
tests (produced by Python generators as `.S` assembly)
   ↓
expected values generated by Sail
   ↓
result verification on a target simulator or hardware
```
Bringing a new extension into ACT4 is, in essence, closing every link of the chain above. The process is gated by two successive bars:

- **The Freeze bar** — the minimum set of deliverables required for the extension to enter the frozen state. It guarantees that the tests can actually be run and that reviewers have solid ground to evaluate them.
- **The Ratification bar** — the complete set of deliverables required prior to formal ratification. Coverage, documentation, and cross-implementation validation must all be closed out.

Each deliverable listed in the remainder of this document is annotated with the bar to which it belongs.

## 2. Full Deliverables Checklist

The deliverables are organized by upstream repository for ease of preparation.

### 2.1 Specification repository (riscv-isa-manual)

| Deliverable | Bar | Notes |
| --- | --- | --- |
| A stable, citeable version of the extension specification | **Freeze — required** | Both ACT's YAML files and its CTP anchor on chapter and rule names in the specification; a definite version number and frozen state are therefore required. |
| **Tagged normative rules** included in the specification | Freeze — expected; <br> **Ratification — required** | `coverpoints/norm/<Suite>.yaml` references the rules in the specification directly by name. If a rule listed in the YAML cannot be located in the specification, review cannot proceed. |
| Specification PR merged, or at minimum a frozen branch in existence | Freeze — required | The practical order is: extension frozen → merged into the main ISA Manual → ratification. |

### 2.2 Encoding repository (riscv-opcodes)

| Deliverable | Bar | Notes |
| --- | --- | --- |
| New instruction encodings merged into riscv-opcodes | **Freeze — required** (if new instructions are introduced) | ACT's `disassemble.svh` decoder is auto-generated via `RISCV_imported_decode_pkg.svh`, whose source lives in riscv-opcodes. **Do not hand-edit `disassemble.svh`.** |

### 2.3 Reference models and simulators

| Deliverable | Bar | Notes |
| --- | --- | --- |
| **Sail** support | Freeze — strongly recommended; **Ratification — required** | Pre-ratification submission to Sail is permitted, but the PR must be open and buildable, because ACT relies on Sail to produce expected values. |
| Minimal **UDB** declaration | **Freeze — required** | Even a handful of YAML files declaring the extension's existence (without CSR YAML) is acceptable; without them, the ACT framework has no basis on which to select the relevant tests. |
| Support in at least one ISS (Spike, QEMU, or Whisper) | **Freeze — required** | Without a supporting ISS, the correctness of the tests cannot be verified; reviewers do not accept logs produced by hand-invoking `spike` in non-self-checking mode. |
| GCC or Clang support | Freeze — required | The tests must be compilable; the toolchain is indispensable. |

### 2.4 ACT repository (riscv-arch-test) deliverables

| Deliverable | Location | Bar | Notes |
| --- | --- | --- | --- |
| **Testplan** | Unprivileged: `testplans/<ext>.csv`; privileged: a Google Sheet linked from the CTP is recommended | **Freeze — required** | The testplan is the anchor for every coverpoint and every test. At freeze, it must enumerate every point that will eventually be tested, even if some tests are not yet in place. |
| **CTP section** (AsciiDoc) | Corresponding chapter in `ctp/` | **Ratification — required** (may be omitted at freeze) | Follow the structure of existing privileged CTP chapters; must contain `include::norm/<Suite>_norm_rules.adoc[]`. |
| **Normative-rule → coverpoint mapping YAML** | `coverpoints/norm/<Suite>.yaml` | **Freeze — required** | Every tagged normative rule must map explicitly to a concrete coverpoint. |
| **Parameter YAML** | `coverpoints/param/<Suite>.yaml` | **Freeze — required** | Declares the UDB parameters upon which the suite depends and the coverpoints they influence. **The format must be machine-parseable** — natural-language references such as "all coverpoints" or "all tests" are not permitted. |
| **SystemVerilog coverpoint files** | Unprivileged: `generators/coverage/src/covergroupgen/templates/`; privileged: `coverpoints/priv/<suite>_coverage.svh` plus `<suite>_coverage_init.svh` | An initial version is acceptable at freeze | A "reasonable start" suffices at freeze; substantial elaboration is required before ratification. Unprivileged coverpoints must carry an `iff (ins.trap == 0)` clause or an equivalent constraint. |
| **Python test generator** | Unprivileged: `generators/testgen/src/testgen/coverpoints/`; privileged: `generators/testgen/src/testgen/priv/extensions/` | **Freeze — required** | One dedicated generator per extension, named `<Ext>.py` (see §3.2). |
| **Test files (`.S`)** | Produced by the generator, or hand-written in the suite directory | **Freeze — must be runnable** | Generator-produced tests are preferred; every `.S` file must carry a `START_TEST_CONFIG` / `END_TEST_CONFIG` YAML header that correctly declares `REQUIRED_EXTENSIONS`, `MARCH`, and `params`. |
| **Instruction decoder update** | `disassemble.svh` | Required if new instructions are introduced | Auto-generated from riscv-opcodes; do not edit by hand. |
| **CI configuration** | `config/<group>/`, `ci.yaml`, `run_cmd.txt` | **Freeze — required** | The extension must, at minimum, be exercised end-to-end in one CI configuration (e.g. Spike). |

## 3. PR-level Technical Bars

The clauses below are the hard requirements that reviewers repeatedly enforce on real pull requests. They determine, in practice, whether a PR is merged.

### 3.1 Normative-rule → coverpoint mappings must be complete and distinguishable

**Completeness.** Every rule listed in the YAML must line up with a coverpoint in the SVH file and with the corresponding assembly test. Any broken link — for instance, `.S` and SVH artefacts pertaining to `sfence_ordering` are already present, yet the norm YAML omits the `sfence_vma_ordering` mapping — must be repaired.

**Distinguishability.** Rules that are architecturally distinct **shall not** collapse onto a single coverpoint lacking cross-bin differentiation. Either they are split into separate coverpoints, or they are distinguished by explicit cross-bins. Representative counter-examples and the differentiation dimensions they demand are as follows:

- SUM-related: `enforceNoX` (a fault is expected when SUM = 0 and a U-mode page is accessed) and `sum_effect` (access is expected to succeed when SUM = 1) are complementary conditions; the required cross-bin is `(sstatus_sum ∈ {0,1}) × (page_mode ∈ {U,S}) × (fault ∈ {yes,no})`.
- Matching-related: `match_priority` (first-match-wins when multiple entries cover the same address) and `match_irrespective_perm_bits` (address matching is independent of permission bits) are orthogonal; the required cross-bin is `entry_index × perm_bits × match_result`.
- Out-of-range CSR-related: `oob_read_zero` (an out-of-range read returns zero) and `oob_write_ignored` (an out-of-range write is silently discarded) are entirely different behaviours; the required cross-bin is `(op ∈ {read,write}) × (siselect_oob = yes)`, with explicit coverage of `read_value == 0` and `write_no_state_change`.
- pmpnum-delegation-related: the trio `pmpnum_field` / `pmpnum_zero_delegates_all` / `no_delegation_disables` requires `pmpnum_value × delegation_active × fault_scenario`, with explicit coverage of `pmpnum == 0`.

Should reuse of a single coverpoint be genuinely warranted, the YAML must include a comment explaining why a single point supplemented by bin-level differentiation suffices to cover both rules.

### 3.2 One generator and one test set per extension

A pull request covering multiple extensions (for instance, submitting Sspmp, Sspmpen, and Smpmpdeleg together) must satisfy:

- Each extension has its own Python generator, named identically to the extension: `Sspmp.py`, `Sspmpen.py`, `Smpmpdeleg.py`. The rationale is that the presence of one extension does not imply the implementation of another — Sspmpen, for instance, does not necessarily accompany Sspmp.
- Ad-hoc "single test function" constructs that circumvent the framework **shall not** be used; when finer-grained tests are needed, additional generators should be introduced rather than concatenating tests within a single large file.
- **All** relevant registers must be covered: primary registers exercised in detail and the remaining registers at least included in a smoke test. Testing only the first few registers is insufficient.

### 3.3 Independence and initialization of standalone `.S` tests

Every standalone `.S` file must satisfy:

- **Independent runnability.** No cross-file state dependencies; the file must execute in any order and within any subset of the test suite.
- **Clean state.** Extension-related state (for instance the SPMP / SPMPEN lock bits) must be initialised and cleaned up correctly, with no residue left behind before or after execution.
- **Consistent use of framework macros.** `TEST_*`, `WRITE_CSR`, and `READ_CSR` must be used per ACT4 convention; ad-hoc macros or hand-crafted CSR assembly are not permitted.
- **Correct initialization ordering.** For extensions involving enable / lock / configure sequences, the ordering must be respected (for example, `configure` may not precede `enable`); otherwise the semantics of the test become invalid.

### 3.4 Parameter YAML must be machine-parseable

`coverpoints/param/<Suite>.yaml` may not contain natural-language references such as "all SPMP coverpoints" or "all tests"; these cannot be parsed programmatically. Contributors should align their YAML with the canonical format already established elsewhere in the repository, listing parameter names and the coverpoints they influence in explicit form.

### 3.5 Tests must be executed via the ACT4 framework, with complete logs attached

Logs accompanying the pull request must demonstrate that:

- The tests were executed **via the ACT4 framework** (Sail first produces expected values; the target platform then verifies), rather than being invoked by hand under `spike` in non-self-checking mode. Hand-invoked logs record only an execution trace, cannot verify correctness, and are of limited value at review time.
- Every standalone test executed and returned success.
- The coverage report confirms that every coverpoint is reachable.

### 3.6 Non-blocking practices, strongly recommended

- Establish dedicated coverpoints for **architecturally special cases**. TOR entry 0 (whose implicit lower bound is zero) is one such case; a dedicated `cp_addr_match_tor_entry0` is preferable to conflating it with generic TOR matching.
- **Cross-implementation validation.** Given that Spike, QEMU, and Sail are all linked, verify agreement across implementations on at least three critical scenarios (for instance, TOR entry 0, lock-bit immutability, and permission-independent address matching). Tracking this as a follow-on issue is acceptable.

## 4. Freeze Bar vs Ratification Bar at a Glance

| Item | At Freeze | At Ratification |
| --- | --- | --- |
| Testplan (spreadsheet or CSV) | **Required**, covering the complete set of points | Required |
| CTP section | May be deferred | **Required** |
| Coverpoints | A reasonable start suffices | Substantial expansion required, particularly pass/fail cross-scenarios and complete register coverage |
| Normative rules written into the specification | Ideally already present | **Required**, with YAML references traceable |
| A dedicated generator per extension | **Required** | Required |
| UDB support | **Required** (a minimal declaration suffices) | Required |
| End-to-end execution under the ACT4 framework (Sail-produced expected values → target verification) | **Strongly required** | Required |
| Register coverage | Primary registers in detail plus smoke tests for the remainder | All registers in detail |
| Sail PR | Open and buildable | Merged |
| ISA Manual PR | A stable branch suffices | Merged into mainline |
| Cross-implementation validation | Recommended | Required (critical scenarios closed out) |
| CI | At least one configuration green | Green over the long term |

## 5. Recommended Cross-Repository Merge Order

ACT tests depend on multiple upstream repositories, including the specification, riscv-opcodes, Sail, and UDB; the pull requests across these repositories therefore have natural ordering dependencies. The recommended sequence is:

1. **Specification** (riscv-isa-manual). Complete the extension specification, incorporate tagged normative rules, and reach the frozen state. Formal merge may lag, but the rule names referenced from ACT's YAML must already be finalized in the specification.
2. **Encoding** (riscv-opcodes). If new instructions are introduced, merge their encodings first; the ACT decoder is generated from this source.
3. **Models** (sail-riscv and one of Spike / QEMU / Whisper). Submit the Sail PR (merge is not mandatory, but it must be open and buildable), and ensure at least one ISS supports the extension.
4. **UDB.** Submit a minimal PR declaring the extension and its parameters so that the ACT framework can recognise the extension.
5. **ACT** (riscv-arch-test):
   - Land the testplan (CSV or Google Sheet) and `coverpoints/norm/<Suite>.yaml` first — these serve as review anchors.
   - Follow with the SV coverpoint files, the Python generator, and the `.S` tests.
   - Complete the CTP section prior to ratification.
   - Land the CI configuration last and keep CI green.
6. **End-to-end integration.** Have the target configuration in UDB declare support for the extension → ACT automatically selects the tests → Sail generates expected values → the target platform verifies successfully → complete logs are attached to the ACT PR.

A defect at any step above will be flagged by reviewers on the ACT PR.

## 6. Pre-Submission Self-Check

### Freeze self-check

- [ ] Each extension has its own generator and test files (named `<Ext>.py`).
- [ ] The testplan (CSV or Google Sheet) is complete and covers the full set of points.
- [ ] Every tagged normative rule in `coverpoints/norm/<Suite>.yaml` is mapped to a coverpoint; architecturally distinct rules are differentiated by cross-bins or accompanied by an explanatory comment.
- [ ] `coverpoints/param/<Suite>.yaml` uses the canonical, machine-parseable format, with no natural-language references.
- [ ] Unprivileged SV coverpoints carry `iff (ins.trap == 0)` or an equivalent constraint.
- [ ] Every `.S` file carries the `START_TEST_CONFIG` / `END_TEST_CONFIG` YAML header with `REQUIRED_EXTENSIONS`, `MARCH`, and `params` set correctly.
- [ ] Standalone tests run independently, initialize and clean up extension state (including lock bits) correctly, and use framework macros consistently.
- [ ] UDB carries the minimal declaration of the extension.
- [ ] The suite has been executed via the ACT4 framework (Sail expected values → target verification) and the complete log is attached to the PR.
- [ ] The CI configuration is placed under `config/<group>/`, `ci.yaml` is complete, and at least one configuration is green.
- [ ] Every normative rule referenced from YAML is locatable in the specification.
- [ ] Primary registers are covered in detail; the remainder are at least smoke-tested.

### Ratification self-check (in addition to the freeze self-check)

- [ ] The CTP section is complete and contains `include::norm/<Suite>_norm_rules.adoc[]`.
- [ ] The specification PR has been merged into the ISA Manual mainline.
- [ ] The Sail PR has been merged.
- [ ] Coverage is comprehensive: all pass/fail cross-scenarios covered; every register exercised in detail rather than smoke-tested only.
- [ ] Cross-implementation validation (Spike / QEMU / Sail) succeeds on the critical scenarios.
- [ ] CI has been green over the long term.

## 7. Frequently Asked Questions

**Q: What version status must the specification attain?**
A: At minimum, the frozen version before an ACT PR can be reviewed in earnest; prior to ratification, the specification PR must be merged into the ISA Manual mainline.

**Q: Must the specification carry tagged normative rules?**
A: Strongly expected at freeze and required at ratification. ACT's YAML references rules by name; if the name is not locatable in the specification, the reviewer will reject the PR.

**Q: Is the extension ratified before or after it enters the ISA Manual?**
A: The practical order is: extension specification stabilised → frozen → merged into the ISA Manual → ratification.

**Q: Must the Sail PR be merged?**
A: A merge is not mandatory, but the PR **must be open and usable** — ACT relies upon it to generate expected values. Merge is required prior to ratification.

**Q: Is support in other ISSes optional?**
A: No. At least one ISS (Spike, QEMU, or Whisper) must actually be able to run the tests by freeze; otherwise the correctness of the tests cannot be evaluated.

**Q: Must the UDB PR be merged?**
A: **Required at freeze**, even if only as a minimal declaration (a handful of YAML files stating the extension's existence and parameters); otherwise the ACT framework cannot select the tests.

**Q: Are both the CTP section and the CSV testplan required?**
A: The testplan (CSV or Google Sheet) is required at freeze; the CTP section may be deferred until ratification.

**Q: When are the SV coverpoints required?**
A: A "reasonable start" is required at freeze; substantial elaboration and complete cross-scenario coverage are required prior to ratification.

**Q: Are tests to be generated or hand-written?**
A: Generator-produced tests are preferred (Python, placed under `generators/testgen/src/testgen/priv/extensions/` or `.../coverpoints/`); hand-written `.S` is also acceptable provided it carries the full YAML header and is independently runnable.

**Q: Must CI be green?**
A: At least one configuration must be green by freeze (placed under `config/<group>/` with a complete `ci.yaml`); CI must remain green over the long term by ratification.
