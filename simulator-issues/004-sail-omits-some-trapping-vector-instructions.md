# Sail issue 004: trace omits the trapping vector instruction itself for some illegal-instruction traps

## Summary

When Sail (riscv-arch-test sail config `sail-rv64-max`) takes an
illegal-instruction trap on a reserved vector instruction (e.g. vector destination
register not aligned to LMUL), the resulting trap handling — `mepc`, `mcause`,
trap-vector dispatch — IS recorded in the log, BUT the trapping instruction
line itself ("[N] [M]: 0xPC (0xINSN) <disasm>") is **silently omitted** from the
log for many cases. Without the instruction line, `framework/src/act/sail_to_rvvi.py`
cannot emit an RVVI entry for the trap, so the SystemVerilog covergroup never
samples the test, and the corresponding `*_off_group` / `*_reserved` cross-bin
stays uncovered.

This is observed inconsistently — the same kind of trap (vd unaligned for LMUL>1)
is emitted to the log for some `vd` values but not others within the same test
program, with no obvious pattern related to the encoding.

## Spec / framework expectation

* RISC-V V spec §3.4.2: vector instructions with a register specifier that
  is not aligned to EMUL must raise illegal-instruction.
* `framework/src/act/sail_to_rvvi.py:18` parses lines of the form
  `\[(\d+)\] \[([MSU])\]: 0x([0-9a-fA-F]+) \(0x([0-9a-fA-F]+)\) (.*)` — every
  retired *and* every architecturally-attempted instruction that traps must be
  emitted in this format for the rvvi consumer (SystemVerilog covergroups) to
  sample on it.
* Existing trap-emitting reserved encodings (e.g. masking_vd_eq_v0 covered in
  Issue 001) DO produce both the instruction line AND the subsequent
  CSR `mepc/mcause/mstatus` updates, proving the framework expects this format.

## Evidence

Test program (excerpt from `tests/priv/SsstrictV/SsstrictV_rv64.S`,
generated by `cp_ssstrictv_lmulgt1_off_group.py`):

```asm
SsstrictV_vaadd_vv_cg_cp_ssstrictv_lmulgt1_off_group:           # PC 0x80000670
    vaadd.vv v1, v9, v6     # vd=v1 unaligned for LMUL=2 -> illegal-instruction
    nop
    ...
SsstrictV_vaadd_vv_cg_cp_ssstrictv_lmulgt1_off_group_duplicate_2: # PC 0x800006A0
    vaadd.vv v21, v9, v9    # vd=v21 unaligned for LMUL=2 -> illegal-instruction
    nop
    ...
SsstrictV_vaadd_vv_cg_cp_ssstrictv_lmulgt1_off_group_duplicate_3: # PC 0x800006D0
    vaadd.vv v25, v19, v6   # vd=v25 unaligned -> illegal-instruction
    nop
    ...
```

Sail trace (`work/sail-rv64-max/coverage/priv/SsstrictV/SsstrictV_rv64.trace`)
for PC 0x80000670 — the trapping instruction is **missing**:

```
x8 <- 0x0000000080000674
CSR mepc (0x341) <- 0x0000000080000674
mem[X,0x0000000080000674] -> 0x00000013
[2046] [M]: 0x0000000080000674 (0x00000013) addi x0, x0, 0x0   ...lmulgt1_off_group+4
```

vs. for PC 0x800006A0 (next test, identical reason, same LMUL) — the trapping
instruction IS present:

```
mem[X,0x00000000800006A0] -> 0x2694AAD7
[2179] [M]: 0x00000000800006A0 (0x2694AAD7) vaadd.vv v21, v9, v9   ...duplicate_2+0
CSR mepc (0x341) <- 0x00000000800006A0
```

Confirmed in `work/sail-rv64-max/coverage/priv/SsstrictV/SsstrictV_rv64.rvvi`:
out of 16 LMUL=2 unaligned vd cases generated for `vaadd.vv`, only 2 (vd=v21,
vd=v25) appear in the rvvi. The other 14 are silently dropped.

```bash
# 4 (out of 7 expected)
```

## Coverage impact

All `cp_ssstrictv_lmul{2,4,8}_{vd,vs1,vs2}_off_group` crosses (and equivalent
*_off_group crosses for `vmvnr`, `ls_seg_*`, `narrowing_vs2_*`,
`vrgather_*`, etc.) require the cross fields `vtype_lmul_N` ×
`v{d,s1,s2}_all_reg_unaligned_lmul_N`. Because Sail drops most of the trapping
instructions, only ~6-12% of those cross bins are reachable with the current
rvvi adapter.

## Workaround

None at the test-generation layer — the testgen IS already producing all
required encodings. The fix must be either (a) Sail emitting the trapping
instruction line consistently in its log, or (b) `sail_to_rvvi.py` synthesising
an instruction record for the PC pointed to by `mepc` whenever a trap is
observed without a preceding instruction line.

For the SsstrictV coverage run, the affected `*_off_group` crosses are listed
in `generators/testgen/scripts/priv/_ssstrictv_helpers.py:UNREACHABLE_LIMITED`
(documentation-only — they are not skipped at generation time, so any
improvement to Sail or the rvvi adapter will pick up the coverage automatically).

## Suggested upstream filing

* Repository: `riscv/sail-riscv` (Sail-side fix preferred — instruction-fetch
  path should always log the fetched instruction, even if execution then
  raises an illegal-instruction exception).
* Alternative: `framework/src/act/sail_to_rvvi.py` workaround that synthesises
  a trap entry from observed `CSR mepc/mcause` writes when the most-recent
  instruction line PC ≠ `mepc` value being written.
