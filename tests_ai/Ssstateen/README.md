# Ssstateen: rule-derived tests

The supervisor-level rules of the state-enable chapter (`src/priv/smstateen.adoc`): the `sstateen` and `hstateen`
CSRs as S/HS-mode sees them, and how they gate U, VS and VU. Generated by `tests_ai/gen/gen_Smstateen.py` with
`gen/smstateenlib.py`; the `mstateen` rules are in `../Smstateen` (see its README for the shared method).

How the extension is tested:

- **No machine-level access.** Every test boots to S and never reads or writes `mstateen`, so the suite runs where
  M-mode is the execution environment (RVA23). The machine-level enable of each piece of state is inferred from an
  S-mode probe at the boot configuration (x6), and the hstateen/sstateen bits are read back after each write (x8,
  x9); the expected outcome of every access is computed from them (`smstateenlib.predict`). With Smstateen the boot
  enables all standard state; without it the stateen CSRs themselves may be inaccessible, and the existence tests
  (`sstateen_rv64_csrs`, `hstateen_rv64_csrs`) then accept illegal-instruction.
- **hstateen gating** (`hstateen0_se0_op`, `hstateen0_envcfg_op`, `hstateen0_aia_op`, `hstateen0_context_op`,
  `hstateen0_imsic_op`, `hstateen_bit_63_op`): the bit is set to 1, 0, 1 and the state read from S, U, VS and VU.
  VS/VU accesses the hstateen bit blocks raise virtual-instruction; HS-mode is never affected. `stopei` sets
  `hstatus.VGEIN` = 1 and reads it back; only with a valid guest file may VS-mode access it.
- **sstateen gating** (`sstateen_user_access_control`): JVT (`jvt`) and, without F, FCSR (`fcsr`) for U and VU (VU:
  virtual-instruction when only sstateen blocks).
- **Encodings and crossing.** `hstateen0_enc_img` checks the reserved bits (3-53, 55, 56, 61) and that clearing one
  defined bit changes only that bit's state from VS-mode (sstateen0, senvcfg, siselect, stopi, scontext, sctrctl,
  jvt). `hstateen_encoding` writes hstateen0 = 0 and all ones and checks VS/VU are blocked and allowed while HS is
  not affected. `sstateen0_enc_img` does the same for sstateen0 from U-mode.
- **Masking and bit 63.** `sstateen_vsmode_access_roz` reads and writes `sstateen0` from VS-mode with hstateen0 bits
  cleared and set; `hstateen_bit_63_writable` sets and clears bit 63 of each hstateen (hstateenNh bit 31 on RV32).
- **Own level** (`stateen_op`): with hstateen0-3 and sstateen0 = 0, every HS-mode access has the outcome it had at
  the boot configuration.
- **Reserved bits** (`stateen_reserved_roz`) from HS-mode (hstateen0-3, sstateen0-3) and VS-mode (sstateen0-3).
- **Mutation check:** the gating and structure mutants of `gen_Smstateen.py` (`Smstateen:<name>`) cover these tests
  too (hstateen gating HS-mode, hstateen or sstateen ignored, illegal instead of virtual-instruction, writable
  reserved bits, read-only bit 63, VS-mode `srmcfg`/`stopei` allowed).

Rules not tested here:

- The `mstateen` rules, `hstateen_ro1_bits` (needs `mstateen`) and the M-mode parts of `stateen_op` and
  `stateen_reserved_roz` are in `../Smstateen`.
- `hstateen0_csrind_op` and `hypervisor_impl_csrs_access_control` belong to Sscsrind; `hstateen_ctr`, `hstateen_vs`
  and `hstateen0_ctr0_v1_op` to Ssctr.
- `sstateen_vsmode_access_roz` and the sstateen sweeps hold trivially on every configuration in `config/`: none has
  Zcmt, Zfinx or custom state, so `sstateen0` is read-only zero there and the masking path has nothing to mask.
  They were exercised on scratch Zfinx configurations of Sail and Spike (sstateen0.FCSR and C writable).

Subtleties:

- `sstateen` has no VS-mode substitute: VS-mode reads and writes the same `sstateen` CSRs as HS-mode, masked by
  `hstateen` (a hypervisor must swap them per guest).
- The boot writes only `hstateen0`; `hstateen1-3` keep their reset values, which the tests read back before relying
  on them.
- A VU access blocked only by `sstateen` (with mstateen and hstateen allowing it) is HS-qualified, so it raises
  virtual-instruction, like `scounteren` for counters ([#1528](https://github.com/riscv/riscv-isa-manual/issues/1528)).
- A VS write to `sstateen0` must leave the bits `hstateen0` masks unchanged (they are read-only in VS-mode);
  Spike clears them (`~/act-wt/smstateen-findings.md`).
- `hstatus.VGEIN` is WLRL, so `hstateen0_imsic_op` writes 1 only when `hgeie` bit 1 is writable.
- Known DUT bugs: QEMU lets `sstateen1-3` bit 63 be written on RV64
  ([qemu#4726](https://gitlab.com/qemu-project/qemu/-/work_items/4726)); Imperas let `hstateen0` bit 56 be written and
  kept `hstateen` bit 63 read-only (both fixed in the engineering build).
