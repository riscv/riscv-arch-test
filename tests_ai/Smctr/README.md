# Smctr: rule-derived tests for control transfer records (machine level)

The M-mode parts of the `norm:` rules in `src/priv/smctr.adoc`, as `<rule>_Sm.S` files. Each file boots to M-mode and
requires Sm, so certification profiles without M-mode drop it. They are generated by `tests_ai/gen/gen_Smctr.py`,
which also writes `tests_ai/Ssctr`. The supervisor-level parts of the same rules, and the measurement method, are
described in `tests_ai/Ssctr/README.md`.

**Which DUTs check this suite.** Sail has no Smctr, so the checking DUTs are QEMU 11.1.3 and Whisper 6b8cce1 with
smctr/ssctr enabled. Spike and Imperas have no CTR.

## How the extension is tested

- **Direct M-mode access.** The tests write mctrctl directly; sctrctl is its S-level view. The first lines clear
  mctrctl and vsctrctl, because their reset values are UNSPECIFIED.
- **Delegation.** medeleg[3] and [8..10] are cleared, so ebreaks and the T-SBI ecalls that leave U, S, VS and VU trap
  to M-mode. With mctrctl.M = 0 the M-mode handler is not recorded.
- **VS/VU windows.** VS/VU-mode is entered by a T-SBI GOTO_SMODE to HS-mode and an sret, because MRET into V=1 is
  not usable on QEMU (qemu#4588, #4620). Each window is left with a T-SBI GOTO_MMODE.
- **mctrctl.**
  - Field sweep: U, S, M and BPFRZ are mandatory, and LCOFIFRZ is mandatory with Sscofpmf.
  - The 64-bit read/write behaviour, and the mapping of sctrctl onto mctrctl (M and MTE kept).
  - Recording in M-mode, and mret (TYPE 3) between enabled modes.
- **External traps into M-mode.** S->M, U->M, VS->M and VU->M, each swept over MTE, sctrctl.STE and vsctrctl.STE.
  The intervening modes' enables are required. MTE is probed, and MTE and STE must be implemented together.
- **Freeze.**
  - BPFRZ on breakpoints to M-mode.
  - LCOFIFRZ on real counter-overflow interrupts to S-mode and M-mode, with and without the target mode enabled.
  - vsctrctl.LCOFIFRZ on LCOFIs to VS-mode, either through hideleg[13] (Shlcofideleg, probed) or as virtual LCOFIs
    pended by the hypervisor in hvip[13] with hvien[13] (Ssaia, probed).
- **mstateen0.CTR.** With CTR = 0, every listed operation raises illegal-instruction from S, U, VS and VU (not
  virtual-instruction). This covers all eight CSR forms on sctrctl, sctrstatus, sctrdepth and vsctrctl, sireg* and
  vsireg* with a CTR select, and SCTRCLR, which must not clear the entries. M-mode access still works, transfers are
  still recorded, and hstateen0.CTR is read-only 0.
- **Mutation check.** The mutants are shared with Ssctr (see its README). All are caught.

## Rules not tested, or only partly

- `Smctr_scope`: only the M-mode access to every CTR CSR and SCTRCLR is tested here; the behaviour at the other
  levels is the Ssctr suite.
- `vsctrctl_lcofifrz_op`: the hideleg[13] path is not checked by any available DUT (neither QEMU nor Whisper can
  delegate LCOFI to VS-mode). The virtual-LCOFI path through hvien/hvip runs on both.
- `debug_recording_inhibited`: needs Debug Mode.

## Subtleties

- **LCOFIs come from a real overflow.** mhpmcounter = all ones and the DUT event from `RVMODEL_MHPMEVENT_*`, with no
  xINH bits. QEMU loses counts when xINH filtering is used
  (`~/repros/2026-11-06-qemu-sscofpmf-xinh-stop-loses-count.tar.gz`). The overflow may already happen during the
  M-mode setup; LCOFIP then stays pending until the window enables the interrupt in the target mode. The wait in the
  target mode is a bounded loop, because QEMU's overflow interrupt arrives late. When that mode is enabled for
  recording, the loop's branches before the interrupt are recorded. Then only FROZEN and "the last record is not
  the trap" are checked.
- **QEMU versions.** The ACT CI pin is QEMU 11.1.3. QEMU 11.1.2 (the one on PATH here) does not let mie.LCOFIE be
  written, so the LCOFI tests fail there.
