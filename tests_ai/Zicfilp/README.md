# Zicfilp: rule-derived tests

One test per `norm:` rule about Zicfilp (landing pads): the Zicfilp parts of `src/unpriv/cfi.adoc` and `src/priv/cfi.adoc`, and the ELP/LPE/lpad rules in `machine.adoc`, `supervisor.adoc` and `hypervisor.adoc`. Generated by `tests_ai/gen/gen_Zicfilp.py` (helpers in `tests_ai/gen/zicfilplib.py`).

How the extension is tested:

- **One primitive: jump and land.** Each case transfers control in a trap window (`jalr` with any rs1/rd/immediate, `c.jr`, `c.jalr`, `jal`, `c.j`, `c.jal`, a taken branch or falling through) to a target block, then checks the outcome. The block is the instruction(s) under test, then a 4-byte-aligned `lpad 0`, the recovery landing pad. A trap at the target resumes there (`rvtest_trap_resume`), so the handler's xRET, which restores ELP from xPELP, always returns to a valid landing pad. Landing pads are written as `auipc x0, <label>` and compressed instructions as `.hword`, so MARCH needs neither Zicfilp nor C. Misaligned targets (2 mod 4) and compressed transfers run only `#ifdef ZCA_SUPPORTED`.
- **Observing ELP.** ELP is not readable. LP_EXPECTED shows as a software-check exception (cause 18) at a target that is not a valid landing pad; the window checks the cause, xepc = the target ([#1584](https://github.com/riscv/riscv-isa-manual/issues/1584)), xtval ∈ {0, 2}, the mode the trap came from, and xPELP = 1 in the handler's xstatus (mstatus.MPELP, mstatush on RV32, sstatus/vsstatus.SPELP, whichever handler took it). That ELP was _not_ set is shown by an `ebreak` target taking a breakpoint with xPELP = 0, not just by the absence of a fault.
- **Modes.** Unprivileged rules whose M-mode behavior could differ (`Zicfilp_lpad_expected`, `Zicfilp_lpad_label`, `Zicfilp_lpad_enabled_instr_allowed`) also have `_Sm` files that run them with mseccfg.MLPE=1. Most tests boot to S-mode, enable landing pads in every mode (menvcfg.LPE for S, senvcfg.LPE for U and VU, henvcfg.LPE for VS) and run each case in U, S, VU and VS (H). M-mode parts (mseccfg.MLPE, mstatus.MPELP, medeleg, PMP) are in `_Sm` files that boot to M; they also cover harts without S, where menvcfg.LPE enables U and SPELP is read-only zero, and they guard medeleg/menvcfg/senvcfg/henvcfg with `S_SUPPORTED`/`U_SUPPORTED`/`H_SUPPORTED`.
- **The state machine** (`cfi_*_term`, `Zicfilp_lpad_expected`, `Zicfilp_indirect_branch_lpad`): `jalr` for rs1 in {x1, x5, x6, x7, x8, x9, x14, x15} and rd in {x0, x1, x5, x7, x9}, nonzero and odd rs1+imm, `c.jr`/`c.jalr` for several rs1, and the direct transfers. A fault exactly when the transfer is JALR/C.JR/C.JALR and rs1 ∉ {x1, x5, x7}. Calls still write their link register before the target faults.
- **The landing-pad check** (`Zicfilp_lpad_*`, `Zicfilp_elp_lpad_expected`): every condition alone (non-lpad, misaligned lpad, label mismatch); labels 1, 0xFFFFF, 0x80000, 0x55555, 0xAAAAA and random against x7 with random bits 11:0 and (RV64) 63:32; single flipped label bits; `lui x7` back-to-back with the jump; LPL = 0 with any x7. The label is read after the jump: a `jalr x7` lands on a landing pad built at run time in a data word whose label is the link address's bits 31:12 (then `fence.i`), which must match. Non-lpad targets of every class (ALU, load, store, branch, `jal`, `auipc`/`lui` rd≠0, CSR, fences, `ebreak`, `wfi`, compressed) fault without executing: registers and memory unchanged. A successful lpad clears ELP (`ebreak` after it saves xPELP = 0). With Zicfilp disabled, lpad is a no-op.
- **Traps and xRET** (`Zicfilp_pelp_trap*`, `Zicfilp_pelp_trap_return*`, `*_pelp_op`, `vsstatus_*`, `sstatus_spelp`): xPELP saved by traps into M, S/HS and VS (hedeleg[18], when writable), both 1 and 0; the ELP=0 traps run with xPELP=1 beforehand where that survives into the trap (S to S, M to M, VS/VU to VS), including from a mode whose LPE is 0; `sret` from S to U/S/VU/VS, `sret` in VS, `mret` to M/S/U/VS/VU and `sret` executed in M, each crossing xPELP ∈ {0, 1}, the new mode's LPE ∈ {0, 1} with the other enables set _opposite_ (so reading the wrong enable is caught), and a non-lpad or lpad target. xPELP = 0 after the xRET is checked where it is observable: mret to M, sret to S (from S and from M), sret VS to VS, and sret VS to VU (vsstatus read in HS). sstatus.SPELP aliases mstatus.SPELP when V=0 and vsstatus.SPELP when V=1.
- **Enables** (`menvcfg_*`, `senvcfg_*`, `henvcfg_*`, `mseccfg_*`): each enable is read back, and swept against the others in every mode (enforced exactly where the mode's own enable is 1), including transitions of MLPE. Disabled-mode bullets: ELP not updated (breakpoint with xPELP = 0) and lpad a no-op (mismatched or misaligned lpad).
- **Priority** (`Zicfilp_exception_priority*`, `Zicfilp_forward_trap_async_exception_Sm`): a target that is illegal (or virtual-instruction from VS/VU) in its mode gives cause 18; an instruction access fault (PMP entry with R/W but no X over a code page, probed at run time) gives cause 1 with MPELP = 1.
- **Interrupts** (`Zicfilp_forward_trap_async_interrupt`): an `sret` restores ELP = 1 with a supervisor software interrupt pending, so the interrupt is due at the landing-pad target. The hart may take it there or later; the check is that sepc = target exactly when SPELP = 1, and that the landing pad still lands afterwards.
- **Registers.** x5 appears as a jump register and link register (`jalr x0, 0(x5)`, `jalr x5, ...`), because the rules name x5 as an exempt link register. It is written after `AI_ALLOW` and before the outcome checks, which reload it. No other reserved register is used.
- **Mutation check.** `gen_Zicfilp.py` has 45 mutants (`Zicfilp:<name>`): wrong rs1/rd decode, x7/x5 not exempt, compressed jumps ignored, direct jumps setting ELP, any instruction or misaligned/mislabeled lpad accepted, wrong label field, label read before a `jalr x7`, `auipc rd≠0` as lpad, ELP not cleared by lpad, faults with ELP clear, wrong xtval/xepc, xPELP not saved, ELP leaking when disabled, wrong priority, link not written, wrong delegation, xRET ignoring LPE / not restoring / keeping xPELP / using the current mode's LPE, each enable read from the wrong CSR, read-only PELP and LPE fields, SPELP aliasing errors, MLPE reset to 1, xPELP set but never cleared, xPELP written only when the trapping mode's LPE is 1. Each one fails a test on Sail (sail-rv64-max; `mlpe_reset_one` on sail-rv32-max, which lacks Smmpm).

Rules not tested here:

- `dcsr_pelp_op`, `Zicfilp_pelp_debug_mode`: Debug Mode cannot be entered by an ACT test.
- `mnstatus_mnpelp_op`, `mnstatus_mnpelp_update`, `mnret_Zicfilp` (Smrnmi): no ACT configuration implements Smrnmi (Sail does not), so tests could not be validated; an RNMI cannot be raised by a test at all. `mnret` with `mnstatus.MNPELP`/`MNPP` would be testable from M-mode once a configuration enables Smrnmi.
- `mstatus_spelp_mpelp_enc_lead_in` ("encoded as follows:") has no content of its own; `mstatus_spelp_mpelp_enc_list` tests the encoding.
- The Zicfiss rules that `cfi.adoc` and the greps also return (`Zicfiss_*`, `ss*`, `sspopchk_*`, `sspop_*`, the `shadow stack fault (code=3)` encodings) belong to the Zicfiss suite. `mtval_swchk_list`/`stval_exception_info` are tested only for code 2 (and 0).
- Partly tested: an interrupt exactly between a jump and its target cannot be placed, so `Zicfilp_forward_trap_async_interrupt` uses an xRET that restores ELP (above), in U and S only; VS/VU (hvip.VSSIP) and interrupts taken into M are not generated yet. Instruction page faults and guest-page faults (also above the landing-pad fault) are not tested; the access-fault case is. `mseccfg_mlpe_rst` is observable only without Smmpm, because the framework's boot writes `mseccfg = 0` when Smmpm is implemented. A `jalr` to a misaligned target without C is an instruction-address-misaligned exception on the jump, a different rule.

Subtleties:

- **xtval.** The unprivileged text says xtval is set to "landing pad fault (code=2)", but the software-check xtval list defines 0 as "No information provided", and the platform may make xtval zero for any exception (`norm:mtval_per_exc_behavior`, `norm:stval`). Tests accept 2 or 0, never 3, the target address or the instruction bits.
- **xepc** is the target (the landing pad or the instruction where one was expected), not the jump ([#1584](https://github.com/riscv/riscv-isa-manual/issues/1584)).
- **MPELP is writable** whatever MLPE, and MRET still clears it when MLPE = 0 ([#3331](https://github.com/riscv/riscv-isa-manual/issues/3331)). QEMU and Whisper RV32 made it read-only zero.
- **SPELP is read-only zero without S** ([#3371](https://github.com/riscv/riscv-isa-manual/issues/3371)).
- **menvcfg.LPE = 0 does not make senvcfg.LPE or henvcfg.LPE read-only zero** ([#3142](https://github.com/riscv/riscv-isa-manual/issues/3142)), so the enables are swept independently.
- **MLPE resets to 0** ([#1591](https://github.com/riscv/riscv-isa-manual/issues/1591)).
- **medeleg[18]** need not be writable ([#2675](https://github.com/riscv/riscv-isa-manual/issues/2675)); delegated cases are probed at run time. hedeleg[18] likewise.
- **Virtual-instruction shares illegal-instruction's priority level** in the hypervisor exception-priority table, so it ranks below the landing-pad fault too.
- The framework's own failure path and trap entries begin with `lpad 0`, and its internal jumps go through x7 (software-guarded), so tests may leave landing pads enabled in the handler's mode. Tests clear every enable at the end.
- A VS-mode write of sstatus.SPELP is checked in vsstatus only: whether it left mstatus.SPELP alone is not observable, because leaving VS is an ecall into HS, which rewrites mstatus.SPELP.
- A run-time branch (`TestFile.either`) cannot hold `#ifdef ZCA_SUPPORTED` table entries, so the hedeleg/medeleg-probed cases use a mismatched label instead of a misaligned lpad.
- QEMU bugs the SPELP/xPELP tests catch: with H, SPELP uses the wrong sstatus/vsstatus copy on traps into HS-mode,
  on SRET into VS/VU-mode and with henvcfg.LPE = 0 ([qemu#4822](https://gitlab.com/qemu-project/qemu/-/work_items/4822));
  a trap leaves xPELP unchanged when the trapping mode's LPE is 0
  ([qemu#4823](https://gitlab.com/qemu-project/qemu/-/work_items/4823)).
- Imperas accepts AUIPC with rd ≠ x0 as a landing pad when ELP = LP_EXPECTED (Imperas SolvNet case 500WQ00002HbTRgYAN).
